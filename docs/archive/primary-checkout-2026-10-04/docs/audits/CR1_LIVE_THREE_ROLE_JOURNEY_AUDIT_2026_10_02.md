## 3. Guest-facing truth and usability defects

1. **Contradictory reviews.** The public map card shows `4.8 · 12 reviews` for a listing whose public API fields were `rating:0` and `reviewCount:0`; the detail page correctly says no verified reviews. The map uses `activeListing.rating || 4.8` and `reviewCount || 12` at `components/MapSidebar.tsx:1166-1168`. Zero is a meaningful value and must not become fabricated social proof. **LIVE FAIL + source-confirmed explanation.**
2. **Invented privacy measurements and categorical claims.** The public cards display percentages such as 75% or 100% privacy. `components/ListingCard.tsx` derives fixed `privacyPercent` and categorical explanations from a listing's type/title instead of a reviewed property fact. This is not an acceptable guest promise, especially while verification is unpublished. **LIVE FAIL + SOURCE FINDING.** Remove unsupported percentages and descriptions or bind them to approved, attributable facts.
3. **Map truth.** The fallback map displayed Yogyakarta-oriented labels or generated city street names such as `GOA BLVD`/`GOA AVENUE`. `components/MapSidebar.tsx:95-120` constructs these labels when a live map is unavailable. A decorative sketch must be labelled as such and must not resemble geographic navigation. **LIVE FAIL + source-confirmed explanation.**
4. **Public inventory quality.** A fresh `/api/listings` read returned seven public rows; **all seven** had `isVerified:false`, `hasOffers:false`, `rating:0` and `reviewCount:0`. They included test-like names such as `asdfghjhfff`, `Test Luxury Villa` and `Sensory Atmosphere Deck 2`. The observed detail juxtaposed Berlin and inconsistent travel/amenity language. Publication status alone is not verified inventory. **LIVE FINDING** for this seven-row response; ownership, photo rights and real-world truth still need independent confirmation.
5. **Reserve label conflicts with actual gate.** Cards offer a Reserve affordance while the detail page disables checkout. The public path should say “View stay” or “Ask about availability” until server quote/payment/booking are legally and technically accepted. **LIVE FAIL** for expectation-setting.
6. **Dead control.** The detail Menu button produced no visible action. Its handler contains `/* Future Menu Drawer */` at `components/ListingDetailsNew.tsx:521`. **LIVE FAIL + source-confirmed explanation.** Remove or implement it before claiming a polished navigation experience.
7. **Investor showcase is not operational proof.** `/investor-showcase` contains separately labelled fictional/unbookable concepts by design. The founder does not want a separate sample page used to stand in for the business. Retain its clear isolation for internal design review if useful, but present only consented, approved, real inventory and real role journeys as evidence of operation. The live public catalogue itself still needs cleanup before that demonstration.
8. **Wrong canonical origin.** The live `/api/seo?type=stay&slug=property-10` response is HTTP 200 but emits a canonical and `og:url` under `https://encho.space/stay/property-10`, while the business origin tested is `https://www.encho.co.in`. `server.ts:3455-3459` hardcodes this. This compounds the broken direct-link path and should be corrected from a reviewed canonical-origin configuration with a deployed SEO regression.

## 3.1 Source-level authorization finding before restoring login

`POST /api/listings/:id/calendar` at `server.ts:3328-3355` (also present in `origin/main`) runs `authenticateToken`, then accepts `listingId` from the URL and writes `calendar_prices` without comparing the persisted actor to `listings.user_id` or requiring a scoped Admin authority. It loops over caller-provided dates, price, offer and status, and may request an advertising auto-pause. The adjacent canonical `/room-calendar` service has an owner-scoped contract, but it does not shadow or remove this older route. **This is a P0 cross-listing mutation path in source, conditional on a user reaching authentication and the deployed database grants/RLS permitting the write.** No cross-tenant live mutation was attempted. A pre-cutover mounted regression must prove foreign-host 403/no changes on separate PostgreSQL connections, and the legacy route should be retired or delegated to the canonical owner-checked command without changing historical records.

The generic `GET /api/listings/:id` and `/api/listings?userId=...` handlers also inspect JWT claims directly at `server.ts:14395-14407` and `server.ts:14423-14448` instead of calling the persisted-session resolver used by `authenticateToken` (`server.ts:703-714`). That leaves a source-level stale-role/account-state risk for privileged listing projections. Reproduce it with a revoked/suspended account and replace claim-only authorization with current persisted authority. This is a source finding, not a claim of observed live data exposure.

The read-only Antigravity audit identified the calendar owner-check gap, but its phrasing “unauthenticated IDOR” was inaccurate: the POST **does** require `authenticateToken`. Its claim that both room GET and PUT are absent from deployed `origin/main` was also too broad: `PUT /api/listings/:id/rooms` exists there. Its claim that Host Calendar is not wired to the canonical route is also false for current source: `components/HostCalendar.tsx:39,58` reads and mutates `/room-calendar`. We independently checked these routes before including a finding. Antigravity's proposed feature percentages are not release evidence and are not used here.

## 5. Root cause and worktree disposition

The immediately observed login error is explained by `server.ts` calling global database readiness before authentication; the live readiness response identifies an owner/BYPASSRLS/CREATE-capable connection and incomplete recovery grants. Historical migrations 041–047 were restored to the packaged source and matched the read-only observed applied checksums, but that cannot make a privileged runtime safe. A partially tested restricted LOGIN/grant prototype exists; its Host, Guest, conversation, marketing, worker and Admin route matrix is incomplete. Production should not be switched to that partial role, nor should an `HARVO_ALLOW_OWNER_ROLE` escape hatch be enabled. Complete and rehearse the non-bypass role/grant matrix in isolated staging, then cut over with a rollback plan and independent sign-in/readiness proof.

The Antigravity and Codex working trees are **not deployed automatically**. At audit time the primary checkout is dirty at `6ec5b66` while `origin/main` is `7ab1b19`; this is a source-identity and review risk, not proof that a dirty worktree directly broke Vercel. The direct URL failure and runtime role are deployed behavior. Reconcile which commit and configuration the Production deployment actually uses, and promote only reviewed, committed, tested changes. Do not bulk-merge worktrees to repair a runtime credential or route problem.

## 6. Fix order and independently testable release criteria

1. **P0 — repair listing/calendar authorization before restoring identity.** Retire or owner-scope the legacy calendar POST; exercise foreign host, revoked user, Admin, malformed input and retry against disposable PostgreSQL on separate connections, proving no cross-listing row or campaign-pause effect. Replace direct JWT-claim checks on privileged listing reads with persisted session/owner authority. A working login would make these reachable, so this must precede the live sign-in cutover.
2. **P0 — restore both identity systems without bypassing isolation.** On a named isolated Neon staging branch, create explicit least-privilege runtime LOGIN roles and the full route-specific table/function/sequence grants. Run catalogue checks plus actual Guest, Host, workforce/Admin and worker negative-tenant tests on separate connections; prove migration history authority with a read-only check. Rehearse dedicated workforce Google configuration/session issuer separately from consumer login. Deploy the same reviewed grant set and configuration to the named target under a rollback plan. Production `/api/health/ready` must be ready, and distinct named Guest, Host and invited workforce test identities must complete sign-in with default-deny cross-role tests. No secrets in receipts.
3. **P0 — fix canonical deep links.** Make a direct GET, hard reload and shared link for a published `/stay/:slug` return the approved detail shell/SEO HTML on both domains. Test old `/listing/:id` redirects, unknown/unpublished slugs, canonical tags and SPA navigation in a Vercel preview, then Production. Do not change SEO rewrites blindly; first capture the deployed route match and response headers.
4. **P0 — stop false public claims.** Remove review fallback `4.8/12`, invented privacy percentages and map street names. Require approved media/fact/offer provenance for public cards, detail and SEO. Unpublish/quarantine test-like or unapproved public listings until a real host confirms facts and photo rights; do not erase history. Replace the Reserve affordance while checkout is gated. The same property must render identical approved price/media/conditions across catalogue, detail, SEO and campaign landing.
5. **P1 — close Guest/Host conversation in a real two-account test.** Implement explicit first inquiry with canonical thread ID, selected offer/date/party context, one held-connection message+notification intent, stable replay UUID, post-login return to composer, exact-thread navigation, host reply, guest reconnect/read and actor-switch fencing. Prove scoped support assignment and visible Encho reply only after IAM/privacy policy. Treat socket delivery as a hint, not device reach.
6. **P1 — complete canonical booking only after commercial/legal approval.** One real consented room offer, immutable accepted price/conditions/media, atomic inventory hold, server quote/tax, signed payment capture, booking confirmation/calendar and refund/unknown-outcome recovery. Keep checkout gated until written Indian CA/tax-lawyer and commercial decisions plus staged transaction evidence exist.
7. **P1/P2 — complete Host/Admin campaign path without spend.** Authenticate scoped staff; bind an accepted offer and creative to an immutable revision and funding contract; review exact bytes, paused-create through an approved account, authenticated readback, desired/observed state and reporting windows in both workspaces. Test single-flight pause/recovery and four simultaneous flights with isolated meters. A top-up requires accepted incremental quote, verified capture, ledger reservation, provider budget amendment/readback and unknown-outcome reconciliation; do not revive retired refuel routes or activate spend for a demo.
8. **Release proof.** Run targeted failing-before/fixed-after tests during each repair; at exit run the prescribed full suite, typecheck, lint, isolated build, real mobile/desktop Chrome, separate-login RLS tests, runtime smoke, direct-link checks, customer-consented one-property rehearsal and incident rollback drill. Keep synthetic design assets and real operational evidence separate.

## 7. What can be shown today

The current live site can be shown as **a visual prototype of public browsing** with a candid explanation that sign-in, booking and managed Ads operation are not ready. It should not be presented as a functioning Guest/Host/Admin business platform or real booking proof. Before an investor operations demonstration, first repair authentication and the stay deep link, remove false claims/test inventory, and run a consented real-property Golden Path with recorded receipts. The separate fictional showcase cannot fill those gaps.

**Audit method:** Chrome public navigation, direct-route and sign-in checks; live readiness/API boundary checks; focused source and current Git identity inspection. No full regression suite, authenticated Host/Admin session, mobile accessibility test, actual payment, provider call, or production mutation was performed for this report.

# CR1 founder evidence collection: six packets, one bounded pilot

**2 October 2026 · Collection instructions, not a clearance or approval.** The [external gate register](CR1_EXTERNAL_GATE_REGISTER.md), [Engineering Constitution](../ENCHO_ENGINEERING_CONSTITUTION.md), [three-sided blueprint](../blueprints/ENCHO_THREE_SIDED_OPERATING_PLATFORM_BLUEPRINT.md) and current review control. No step below authorizes a payment, migration, live campaign, customer message or pilot by itself. Capture the *current* console state and exact environment/account; a screenshot without target identity and timestamp is weak evidence. Menu labels can change. Do not paste passwords, access tokens, database URLs, guest PII or unredacted legal documents into chat or Git.

## A. Prepare a private collection folder

1. In macOS Finder choose **File → New Finder Window → Documents → File → New Folder**. Name it `EnchoSpaceNew-private-evidence`. Keep it **beside**, not inside, the Git repository; the repository's `evidence/` is not ignored by Git.
2. Inside it create `01-resort-offer`, `02-legal-commercial`, `03-provider`, `04-staging`, `05-staff-privacy-support`, and `06-pilot`.
3. Limit access to the founder and named reviewers. Keep originals there; produce redacted review copies when needed. Give engineering the folder/file *paths*, issuer, subject/environment, capture date and scope. Engineering can hash and inspect locally. Do not rename a generated fixture or historical draft “signed evidence.”
4. For each packet make a short index: `Gate ID | artifact path | issuer/signer | dated | exact account/offer/environment | what it proves | what it does not prove | reviewer`. Record only inspected hashes/references in the gate register after independent review.

## 1. One real resort, exact room offer and consent (`REAL-OFFER`)

**Founder/Host clicks and records**

1. Choose **one** resort whose legal operator agrees to a limited Encho staging and future pilot trial. Ask that operator to sign a dated permission naming Encho, the property, photo/video usage, staging/test use, whether Ads may later use the assets, and any time/territory limits. A verbal “yes” or a ListingDetails page is not rights proof.
2. In Encho sign in as the named Host → **Hosting → Listings → Hosting Stays** → open the selected listing's **Edit listing** control. Record the listing ID and public `/stay/{slug}` URL, but do not treat an edit screen as approval. Identify **one sellable room**, not only the resort's minimum “starts from” price. Record the room's stable ID, title, capacity, bed configuration, nightly price in INR, dated price changes, taxes/fees as currently disclosed, minimum nights, cancellation/house rules and current inventory. If an ID or accepted-offer version is absent, label it `UNKNOWN`; ask engineering to establish canonical authority rather than inventing one.
3. Collect dated Host source records for price/inventory (rate sheet, property management or booking calendar) and a media-rights manifest: every proposed image/video filename, creator/rightsholder, permission/license, expiry, and which exact room/facility it depicts. Check that the image is truly this property and the claim is true.
4. Open the public `/stay/{slug}` as a Guest and capture the visible room, price basis, photos and conditions. Open the Admin listing/media moderation view and capture its status for the same listing. Mark disagreements; do **not** use a screenshot to certify a bookable offer while the current guest checkout is disabled.
5. Record named **Host, Guest and Admin test account IDs** and who controls them. Keep credentials in a vault; do not send them in the packet. Identify the property's own on-call contact for inventory or guest-safety incidents.

**Sufficient packet:** signed real-host authorization, exact listing/room identity, dated room price/inventory/terms, media-rights manifest and three-surface discrepancy notes. This packet permits engineering to test truth; it does **not** approve payment or ads.

## 2. Indian legal opinion and commercial policy (`LEGAL-01`, `COMM-01`)

**Founder/Finance clicks and records**

1. Open a fresh document titled `Encho India marketplace, bookings and advertising money flow — questions for counsel`. Attach a diagram of Guest quote → payment/capture → accommodation supplier → host payout/commission; and Host ad quote → funding → Encho/provider spend → top-up/under/overdelivery → unused amount/refund. Use **real proposed behavior**, not claims from historic generated receipts.
2. Include three example transactions: ordinary room booking and cancellation/refund; ₹10,000 ad cost with the already-directed 3–5% cost-plus markup (tax treatment **to be determined**); and campaign pause with unused/overdelivered media funds. Include invoice samples showing the question of **who invoices whom**. Do not insert GST/TCS/TDS rates by copying old project documents.
3. Email the packet to a practicing Indian CA **and** a tax/commercial lawyer. Request a signed, dated written opinion identifying each professional, relevant qualifications, Encho's and the Host's legal roles, jurisdiction/effective date, assumptions, statutory treatment of accommodation/commission/ad services, GST/withholding/TCS/TDS if applicable, invoice issuer, payment collection and payout, cancellation/refund/credit note, chargebacks, unused ad funds, record retention and changes that would invalidate the opinion. The [CBIC TCS guidance](https://cbic-gst.gov.in/pdf/FAQs-TCS-30-11-2018.pdf) is a question source, not a substitute for advice tailored to Encho's exact money flow.
4. Separately have Founder + Finance sign a **versioned commercial policy**: definition of recognized campaign cost `C`, permitted markup `p`, rounding, fee/tax display, host acceptance/expiry, exact top-up quote, provider spend variance and overdelivery liability, unused balance refund versus any separately accepted credit, cancellation/refund timing and worked examples. Record the policy version and effective date. An internal draft does not replace the professional opinion.
5. Store signed originals in `02-legal-commercial`; give engineers document names/paths. Reviewers compare the final policy to actual quote, ledger, invoice, payout, refund and top-up code before changing `LEGAL-01`/`COMM-01`.

**Do not sign or reuse** historical generated “legal clearance” receipts or the old [pilot charter](../compliance/TRACK_4_BOUNDED_PILOT_AGREEMENT_AND_STOP_LOSS_CHARTER.md) unchanged. That charter asserts unverified rates/property/caps, a non-refundable wallet and guaranteed outcomes that conflict with the current gate register and Constitution.

## 3. Google and Meta account-owner/API evidence (`PROV-G-01`, `PROV-M-01`)

### Google — current access is attached to the Cloud project

1. Sign in to the **Google Ads manager account**. Click **Accounts → Sub-account settings**. Capture the manager customer ID and the **exact serving/client Ads account** intended for the resort. The manager ID and serving-account ID are different roles. In the client, click **Admin → Access and security → Users** and **Managers**; capture the named operator role and manager ownership/link. [Manager navigation](https://support.google.com/google-ads/answer/7519705), [account links](https://support.google.com/google-ads/answer/7459601).
2. In [Google Cloud Console](https://console.cloud.google.com/google/ads-apis/overview), select the project that **owns Encho's Ads OAuth credentials**. Open **Google Ads API Overview**. Capture project ID, current Test/Explorer/Basic/Standard access level, any feature/permissible-use limits and date. **Test cannot operate production advertiser accounts.** Google [sunset developer tokens on 9 September 2026](https://developers.google.com/google-ads/api/docs/api-policy/developer-token); an old Ads API Center screenshot is historical, not current access proof. [Current access levels](https://developers.google.com/google-ads/api/docs/api-policy/access-levels).
3. Ask engineering to perform a **read-only** API identity/hierarchy query using the real Encho service identity and manager login context. Save sanitized response/request IDs showing the same Cloud project, manager and serving account. UI membership alone does not prove API calls work. [Google call identity](https://developers.google.com/google-ads/api/docs/concepts/call-structure), [hierarchy example](https://developers.google.com/google-ads/api/samples/get-account-hierarchy).
4. Have the actual Ads account owner sign a narrowly scoped authorization naming the **serving customer ID**, app/project identity, named operator, one listing/campaign revision, time window, `PAUSED` create and authenticated readback **only**, zero activation/zero intended spend, emergency stop contact and evidence location. Only after this and engineering's fail-closed checks may a canary be executed. Capture the API request ID, returned resource ID and a fresh readback confirming the exact customer/resource remains `PAUSED`. A screenshot of OAuth branding is not this proof. [Google status definition](https://developers.google.com/google-ads/api/reference/rpc/v25/CampaignStatusEnum.CampaignStatus).

### Meta — account assets and permissions must align

1. Sign in to Meta Business Suite and select the **exact Encho business portfolio**. In its current **Settings/Business settings** interface, find **Accounts → Ad accounts**, **Pages** and **Instagram accounts**; also inspect **People/System users** and the Encho app's permissions/review. These menu labels are conditional because Meta's signed-in UI changes. Capture portfolio/ad-account IDs, ownership and assignments, Page/Instagram asset bindings, app mode/review and `ads_read`/`ads_management` status. Prior Encho screenshots showed business verification but **Access verification not verified**; capture its current state rather than assuming it changed.
2. Open Meta Ads Manager with the selected account and record the `act_...` ID shown in the account selector/URL. Ask engineering for a **read-only** AdAccount API response (ID, name and `account_status`) under the actual app/system-user identity. The [official Meta Marketing API collection](https://www.postman.com/meta/facebook-marketing-api/collection/0zr4mes/facebook-marketing-api-mapi) distinguishes required access/permissions. Do not share access tokens or app secrets.
3. Have the actual business/ad-account owner sign the same bounded **PAUSED-only** authorization, naming business, ad account, app, Page/Instagram asset, exact listing/creative revision, operator/window and stop contact. The engineering canary must create **campaign, ad set and ad all PAUSED**, then independently read back configured/effective status and account identity. Do not copy an example that activates a child resource. Retain sanitized API trace IDs, timestamps, IDs and campaign-specific zero-spend observation; account-wide zero is not the test. [Meta's API collection](https://www.postman.com/meta/facebook-marketing-api/documentation/0zr4mes/facebook-marketing-api-mapi?entity=request-31691153-75199fc3-314d-40ef-895b-3edbcf37ef06).

**Stopping point:** Gathering screenshots and signed scope is safe and read-only. Do not click Publish/Enable/Activate, change billing, create customer-facing ads or run a canary merely to produce evidence. Engineering verifies provider capability, policy category, funding and stop controls before the owner-authorized paused operation.

## 4. Isolated Neon staging and real restricted roles (`ENV-01`, `DB-01`)

1. Open [Neon Console](https://console.neon.tech) → select Encho project → **Branches → New branch**. Confirm the **parent branch** before clicking Create. Name a separate branch such as `staging/encho-cr1`. Choose **Schema only** to avoid copying live customer data; choose **Current data** only under a privacy-approved anonymization/access plan. If a one-day auto-delete option is enabled, disable it for an explicitly long-lived staging branch. Click **Create** and record project/branch ID, parent and creation time. [Neon branching](https://neon.com/docs/manage/branches).
2. In **Connect**, select that staging branch, compute, database and role. A new Neon branch initially carries the parent's roles and passwords; rotate/replace staging credentials before treating it as isolated. Store staging credentials in an ignored, staging-only local secret file or secret manager; do **not** replace `<repository-root>/.env`, and do not send any URL/password. Capture the **file name and branch name**, not the secret value. Migration operations may need a direct rather than pooled connection. [Neon connection guide](https://neon.com/docs/connect/connect-from-any-app).
3. Stop and hand the branch to the DB engineer. Neon [documents](https://neon.com/docs/manage/roles) that Console/API/CLI-created roles inherit `neon_superuser`, which can bypass RLS. **Do not use Roles → Add role for restricted runtime users.** Have the engineer create separate migration-owner and web/worker/issuer LOGIN roles with reviewed SQL and least-privilege grants on the staging branch. Do not paste permanent passwords into Neon SQL Editor, which retains query history. [Neon database access](https://neon.com/docs/manage/database-access).
4. Each actual web/worker/issuer login must produce a read-only receipt showing `rolsuper=false`, `rolbypassrls=false`, no `neon_superuser`/owner membership or `SET ROLE` path, expected grants and `FORCE RLS`; then pass adversarial cross-tenant reads/writes and worker tests. A role-name screenshot is insufficient. A schema-only branch does not carry `schema_migrations` rows; engineering must reconcile migration history **before** any runner invocation.
5. Rehearse backup/restore **to another isolated branch**, record owner and result, and prove the same built artifact against staging with outbound payment/ads/messages disabled until their gates are separately cleared. [Neon backup/restore](https://neon.com/docs/postgres/backup-restore/backups).

# HARVO — booking conversion delivery completion

Date: 2026-09-13. Scope: marketing measurement, provider conversion delivery and recovery. This record separates verified source, implementation work and external acceptance. It does not accept guest M5/M6B or a paid-booking launch.

## Verified current boundaries

Constitution section 20 and the guest decision register require authoritative captured-payment evidence for booking confirmation. Guest M5 and M6B remain legally blocked pending written Indian tax/legal acceptance. Existing `server.ts` calls the retired conversion helper when creating a booking request; that helper is unconditionally disabled. The legacy `GoogleOfflineConversions` scanner treats `bookings.status='CONFIRMED'` and `total_rent` as upload authority. It has neither the accepted canonical capture/quote/consent lineage nor per-item upload evidence. Neither is a valid booking verifier, and this work will not reactivate them.

The new `MarketingMeasurementService` already has immutable canonical event/booking/order evidence, integer amounts, tenant ownership, monotone refunds, current consent rechecks, and a durable outbox. It requires injected `verifyBooking` and `uploader` ports. Unknown dispatches are quarantined; a local timeout cannot undo a provider request. No trusted production booking verifier or consent/attribution resolver is currently connected.

Google's current docs direct new offline conversion integrations to Data Manager; prior Google Ads click-upload eligibility cannot be assumed. Data Manager ingestion returns a request ID before downstream processing finishes. Request-status diagnostics must establish delivery, not the initial 2xx. Google supports order-ID restatement/retraction through its Ads API with account/action restrictions. These primary references are the implementation authority: [offline conversion restriction](https://developers.google.com/google-ads/api/docs/conversions/upload-offline), [Data Manager event ingestion](https://developers.google.com/data-manager/api/reference/rest/v1/events/ingest), [request status](https://developers.google.com/data-manager/api/reference/rest/v1/requestStatus/retrieve), [Google adjustments](https://developers.google.com/google-ads/api/docs/conversions/upload-adjustments).

## Impact and implementation plan (before code)

1. Add isolated provider transports behind the existing `ConversionUploader` contract. Google purchases use Data Manager v1; corrections use Google Ads v25 where supported. Meta purchases use versioned CAPI. A one-event/one-destination request permits honest per-item acknowledgement; no aggregate batch response can silently approve foreign or missing items.
2. Add migration `013_harvo_marketing_conversion_delivery.sql` (number coordinated with the root integration owner) for durable provider delivery claims, bound destination/payload fingerprints, safe receipts and append-only diagnostic evidence. Persist the claim before external I/O. Never persist raw click IDs or contact details in this table. A lost response or commit remains quarantined; there is no automatic takeover of a dispatched mutation.
3. Require an explicit trusted attribution/consent resolver before serialization. Bind booking, order, host, property, campaign, provider, consent record and attribution reference. Never invent identifiers or map unknown/denied user-data consent to granted. Keep provider tokens inside server transport and out of returned evidence/logs.
4. Add a durable consumer that uses the measurement service's current-booking check, drives uploads and performs read-only Google diagnostics for known request IDs. Pending processing is distinct from accepted ingestion; acknowledgement is not attribution, a booking guarantee or proof of incremental lift. Correction dependencies and provider limitations remain explicit.
5. Inspect canonical checkout source and implement an adapter only if accepted authority and legal permission exist. Current evidence does not satisfy that condition. Provide precise readiness blockers and leave missing source ports disabled while implementing and testing executable delivery paths using isolated fixtures. A configuration string is not legal/checkout acceptance.
6. Verify with real disposable PostgreSQL and injected provider HTTP responses: ownership/consent bindings, deduplication, concurrent claims, crash/timeout ambiguity, partial/malformed acknowledgements, asynchronous diagnostics, corrections, permanent failures and no PII/token persistence. No live provider write, payment, external DB mutation or application-server import.

Root owns runtime/router/server wiring and targeting work. This task owns measurement/conversion modules, migration013, tests and this report. No guest schema, quote pricing, checkout state machine, tax decision, public tracking endpoint or customer disclosure is modified.

## Risks and rollback

Provider destination/account permissions, consent wording and accepted checkout integration require live and legal acceptance. Meta's standard Purchase ingestion must not be falsely presented as an adjustment/deletion API; unsupported corrections must be exposed for manual/provider remediation while canonical internal net booking truth remains corrected. Data Manager diagnostic visibility and processing delays must be handled without replaying writes. Unsupported or stale API response shapes fail closed.

Rollback disconnects the new consumer and retains immutable evidence/outbox/delivery records. Never restore the legacy conversion scanner or drop conversion history. Production enablement remains blocked until the missing canonical capture, attribution and consent authority is accepted and wired.

## Implementation and verification results

Implemented `src/lib/marketing/conversions/{contracts,http,providers,store,consumer}.ts` and migration013. The factory `createConversionConsumer(pool, options)` returns `measurement`, `readiness()`, `ingest(reference)` and `runOnce(limit=10)`. Options require an explicit audited service actor, a canonical booking verifier and a canonical attribution/current-consent resolver before the consumer can run. Missing authority returns precise blockers without database or provider activity. The root integration owner controls runtime and sequential worker maintenance wiring; there are no independent timer loops.

Google configuration distinguishes conversion-action owner from serving account. Purchases use Data Manager v1 with an OAuth grant that actually permits Data Manager access. Known processing request IDs are polled read-only and bound to the exact destination, action and single-event count. Google corrections use v25 order-ID restatement/retraction and verify the returned item; wbraid adjustments and provider timing/action restrictions remain explicit rejection/remediation cases. Initial ingestion acceptance does not establish attribution or incremental bookings. No automatic retry of a possibly sent mutation occurs.

Meta uses Graph v26 Purchase ingestion with a stable per-order event ID. Exactly one accepted event and a provider trace receipt are required. The strict resolver contract accepts consented fbc/fbp or a hashed external ID and explicit browser user agent; it accepts no email, phone or raw IP. Ad-user-data and measurement consent must be granted. Unknown, denied or revoked personalization becomes attribution-only `opt_out: true`, supported by the [official Meta server-event implementation](https://raw.githubusercontent.com/facebook/facebook-nodejs-business-sdk/main/src/objects/serverside/server-event.js). Meta's generic Purchase endpoint is not represented as a refund, adjustment or deletion service; corrections remain internal canonical truth plus an explicit provider-remediation status. The application conservatively rejects purchases older than seven days; provider/account acceptance still needs live verification.

Claims are committed before HTTP. Safe receipts, destination and payload hashes are durable; raw click/contact identifiers and credentials are not persisted in delivery evidence. Lost responses, conflicting acknowledgements or lost final commits cannot trigger an automatic replay. Accepted/rejected durable evidence can repair an abandoned outbox dispatch after its active deadline; a claim without an acknowledgement remains quarantined.

The consumer starts bounded independent read-only diagnostics together, then awaits all durable observation writes. A failed write is surfaced only after the whole batch settles. This avoids multiplying serial provider timeouts while the shared worker's control queue waits. Two pure scheduling regressions verify concurrent read start, complete write awaiting and safe persistence-failure reporting; they do not replace the real PostgreSQL delivery tests.

On 13 September 2026, the combined isolated run passed **96 tests**: **47 conversion delivery tests and 49 existing measurement tests**, in 86.81 seconds. Command: `npx vitest run --config vitest.marketing-m1.config.ts src/test/harvo/conversion_delivery.test.ts src/test/harvo/marketing_measurement.test.ts`. Tests used disposable local PostgreSQL and injected HTTP fixtures; no live conversions, external database writes or payment activity occurred. Coverage includes concurrent claims, item-bound acknowledgements, malformed/partial/foreign provider results, asynchronous diagnostics, current consent, PII exclusion, corrections and failure after provider receipt but before local persistence. This proves the executable delivery boundary locally; it does not accept canonical guest checkout, consent collection, OAuth/account eligibility or production booking performance.

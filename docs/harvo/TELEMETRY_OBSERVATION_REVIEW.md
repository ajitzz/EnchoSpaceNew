# Telemetry and campaign monitoring — independent proposal review

20 September 2026 · Source baseline `e832db6` plus preserved worktree · Engineering design refinement; implementation pending.

## Product authority and review scope

The founder explicitly requires Encho to be the host's complete campaign monitoring interface. Hosts must not need Meta Ads Manager, Google Ads, Business Manager or MCC knowledge. Hosts and admins must see valid, automatically updated campaign status and outcomes inside Encho. This reinforces the master-account/no-host-Ads-OAuth model. It does not authorize invented metrics or a promise that delayed provider reports are instantaneous.

The pasted Gemini telemetry report is a suggestion, not an incident certificate. Reviewed source: provider telemetry and delivery methods, engine/queue/scheduler, worker supervision, workflow projections, host/admin studio consumers, canonical measurement/conversion services, and relevant tests. A bounded inspection of legacy CRM/analytics identified candidates and trust issues, not certification of their entire pipelines. No live provider response, deployment log, production database or campaign 8 record was inspected. No production source changed during this review.

Controlling references: [Constitution](../ENCHO_ENGINEERING_CONSTITUTION.md), [HARVO](../../HARVO.md), [decisions](DECISIONS.md), [remediation plan](../implementation/HARVO_PRODUCTION_REMEDIATION_PLAN.md), [previous Gemini review](GEMINI_ARCHITECTURE_REVIEW.md).

## Findings and verdicts

| Claim | Verified source and qualification | Verdict |
|---|---|---|
| Empty provider reports fail telemetry | Meta `fetchTelemetrySnapshot()` rejects absent/surplus/invalid rows with `META_TELEMETRY_UNAVAILABLE`; Google rejects a non-single matching result with `GOOGLE_TELEMETRY_UNAVAILABLE`. Both also validate values/identity/currency | Accept a distinct no-report outcome; never convert arbitrary absence, malformed responses or auth errors to zero. |
| Eight failed attempts permanently stop campaign monitoring | `jobs.ts:fail()` sets a telemetry job DEAD at attempt 8. However, `engine.ts:scheduleObservations()` can enqueue a later observation when no PENDING/RUNNING/RETRY telemetry job remains and the workflow qualifies | Reject “permanently” at campaign level. Distinguish terminal job history from ongoing observation scheduling. Retry intervals, workflow state and queue load affect the next check. |
| Campaign 8's `GOOGLE_INVALID_ARGUMENT` proves empty reporting | Empty rows use a different error code. Invalid dates/query/other arguments require the original request window and safe provider error evidence | Unproven cause. Do not diagnose this live record from the quoted queue label. |
| Telemetry failure bypasses budget protection entirely | The post-snapshot spend calculation is skipped, but `protectBeforeObservation()` checks local inventory/listing first. The catch path enqueues a fail-closed PAUSE for LIVE/PROVIDER_REVIEW with a known provider ID | Partly valid reporting gap; incorrect implication that no protection exists. A queued pause is not confirmed remote stop. Normal empty reports may currently cause avoidable pause churn. |
| Leads/bookings/profile visits remain empty | Engine writes `leads:null, bookings:null`; workflow omits `profileVisits`. Studio displays these as dashes | Verified wiring/product gap. Correct sources are internal authoritative outcomes; provider conversion totals cannot substitute. |
| Polling cadence differs | Visible UI polls workspace every 30 seconds; worker maintenance schedules observations every 300,000 ms. Scheduler selects at most 100 eligible rows per sweep and processing competes with other jobs | Verified, but different cadences are not intrinsically a bug and neither interval is an end-to-end freshness guarantee. |
| No on-demand telemetry mechanism exists | `POST /api/marketing/v2/campaigns/:id/refresh` already queues a scoped five-minute-keyed observation. Studio “Refresh evidence” buttons only reload the workspace GET; they do not invoke that POST | API exists; actionable UI and job/result receipt are missing. Raw provider response access is not a safe dashboard requirement. |

Google documents zero-row omission for reporting and metric-dependent delays. Its current general freshness guidance describes a typical one-hour SLO for clicks/impressions/cost, with other metrics taking longer and later adjustments possible. Gemini's fixed 2–4-hour Google range is not a universal contract. The current query filters `segments.date` without selecting it; preserve its actual query semantics and verify zero-row cases rather than assuming daily segmented rows. [Google zero metrics](https://developers.google.com/google-ads/api/docs/reporting/zero-metrics), [Google freshness](https://support.google.com/google-ads/answer/2544985?hl=en).

The Meta Insights documentation endpoint could not be retrieved during this review. The claimed universal 15-minute–2-hour Meta window is not accepted as a verified SLA. Distinguish an observed empty API response from a claim about why it is empty.

## Additional source findings missed by the proposal

1. **Enabled delivery remains UNKNOWN.** Google `fetchAuthoritativeDeliveryTruth()` deliberately limits its result to paused/removed preparation truth and overrides other states to UNKNOWN, with `isLive=false` and `isServingImpressions=false`. Meta's method returns PAUSED when a hierarchy member is paused, otherwise UNKNOWN with the same false flags. Current read methods cannot establish serving. Replacing them with `ACTIVE=true` would be equally wrong: enabled configuration, eligibility and delivery evidence are different.
2. **Status depends on report success.** Engine reads delivery truth and then telemetry before persisting either. A report failure loses a successful status observation from that attempt. Persist independent evidence under consistent revision/account/control-version guards; do not discard one valid lane because another failed.
3. **Freshness is lost in projection.** Engine stores `freshness`, `dataAsOf`, date boundaries and provider-attributed conversions, but `workflow.project()` omits them. Provider adapters set fetch time to now and `dataAsOf:null`. A recently fetched delayed report is not current underlying delivery or final spend.
4. **Budget freshness is narrower than the report implies.** `assessBudgetProtection()` tests age of `observedAt` and a fixed headroom heuristic. Current adapters just set that timestamp to now. Repeatedly fetching delayed figures can therefore look recently observed without proving recent spend coverage. Its own source warns it is not an exact remote spending cap. Do not call the protection or ledger mathematically sufficient for operational loss bounds.
5. **Useful measurement code is disconnected.** `normalizeMarketingTelemetry()` already preserves source timestamps, units, missing values and fractional attribution; the inspected v2 engine/projection does not use it. `MarketingMeasurementService.bookingTruth()` provides scoped counts/amounts from verified recorded events, explicitly `completeness: NOT_ESTABLISHED`; no production caller was found. Its `capturedBookings` counts recorded orders including those later cancelled/refunded, so labels must express lifetime captured versus current net outcomes. It is not a drop-in “confirmed bookings” total.
6. **Legacy counts cannot be imported without validation.** `performanceAnalyticsService.ts` derives booked/confirmed lead-status counts from `host_outreach_leads`, not accepted checkout captures. The legacy lead verifier includes a fallback signing secret and the inspected ingress uses timestamp-derived dedupe identity. Before reusing any legacy lead data, audit/authenticate ingress, stable event dedupe, campaign bindings, tenant scope, retention and actual worker ownership. No exploit or production ingestion outcome is asserted here.

## Intended monitoring contract

Maintain four independent, tenant-scoped views. Their states must not collapse into a single LIVE badge or one timestamp.

| View | Authoritative source | Host sees | Admin additionally sees |
|---|---|---|---|
| Campaign status | Current authenticated hierarchy/account observations plus exact operation history | Scheduled, under review, eligible, delivery observed in a stated window, paused, needs attention or status unavailable; last check and next action | Safe provider reason/subcodes, bound identities, control operation and observation evidence |
| Ad performance | Validated provider report for exact account/campaign/window/timezone | Impressions, clicks, CTR, reported ad spend, optional supported network-attributed outcomes; coverage/freshness | Request correlation, response classification, quota/backoff and report-window diagnostics |
| Encho outcomes | Verified campaign-linked first-party visits/inquiries and canonical booking/capture/correction events | Property visits, qualified inquiries, captured bookings, fulfilled stays and refund/cancellation effects where measured | Pipeline coverage, lag, attribution-policy version and ingestion/correction exceptions |
| Funds and safety | Canonical finance ledger, authorization and reconciled billing | Paid amount, reserved budget, available/refundable funds, protective pause status; reported spend identified as provisional | Exposure assumptions, stale-report alarms, pause verification and settlement evidence |

Proposed per-lane envelope: `status`, `reasonCode`, `lastAttemptAt`, `lastSuccessAt`, `nextCheckAt`, `observedAt`, `dataAsOf` when actually supplied, report window/timezone, source, completeness, account/revision binding and safe correlation/observation version. Preserve the last valid snapshot separately from the latest attempt outcome. Do not stamp old values with the new fetch time or claim `dataAsOf` equals `observedAt`.

Reporting states should distinguish `NOT_STARTED`, `NO_REPORT_YET`, `AVAILABLE`, `STALE`, `RATE_LIMITED`, `UNAVAILABLE`, `INVALID_RESPONSE` and `NOT_CONNECTED` where appropriate. These are proposed contract values, not existing enums. A valid numeric zero is shown as 0 for its stated window. A successful empty report means no rows returned; it does not prove zero actual spend or impressions. “Learning/calibrating” is displayed only when supported by provider status. A previous positive observation is never overwritten with fabricated zero because a later report is empty.

The frontend presents plain language and bounded actions. Examples: “Google is reviewing your ad,” “Enabled; waiting for delivery evidence,” “Waiting for Facebook & Instagram's first report,” “Reporting delayed; last available report shown,” “Encho has requested a protective pause,” or “Paused — confirmed by the network.” Each is selected from evidence, not used as a default optimistic message. Technical account identifiers and raw error codes belong in role-scoped admin diagnostics, not the normal host journey. Host support and campaign actions remain inside Encho.

## Implementation design within the existing plan

### T1 — Separate status, reporting and safety outcomes (R5/R6)

- Add a typed observation result distinguishing a well-formed empty response from invalid data, request errors, permission failures and transport unavailability. Keep provider identity/currency/ownership checks mandatory. Successful empty reads can complete their read job and schedule an ordinary next observation without incrementing an exception budget; transport failures use bounded jitter/backoff. Deterministic invalid requests create actionable remediation, not an indefinite hot retry loop.
- Persist independent status/report attempt evidence and last-good snapshots with transactional fence/revision/account checks. Introduce or reuse a control-operation version so a slow observation cannot overwrite a newer pause/resume. Unknown status remains unknown even if cumulative metrics exist.
- Complete provider-specific status mapping using the supported hierarchy, account, policy and schedule fields. Establish recent delivery only from explicitly scoped reporting evidence; lifetime impressions are not proof of current serving. Preserve provider reason detail safely and handle partial eligibility.
- Fix future-date windows at scheduling boundaries and use provider account timezone consistently. Include/exclude end dates explicitly across provider API and internal normalizer; their current date conventions differ. Retain original query precision (including Google cost micros) before rounded display amounts. Reuse/test existing normalizers with explicit CTR ratio/percent conversion, rather than introduce incompatible calculations.
- Continue local inventory/price checks without waiting for reporting. Unknown or stale spend never authorizes additional funding, automatic resume or limit increases. Keep the current fail-closed safety behavior until a tested provider-specific exposure policy is accepted. A future first-report grace period needs a bounded loss/exposure budget, verified external limits, freshness assumptions and confirmed stop escalation; an arbitrary 2–4-hour sleep is not acceptable. Configuration of an external cap is not proof of complete cost settlement.

### T2 — Fair scheduling and controlled refresh (R5/R6/R8)

- Separate due times and failure budgets for status, reporting and protection. Use bounded concurrency, provider/account quota budgets, Retry-After support, jitter, durable fair pagination and coalescing across periodic/manual/webhook triggers. Safety/control must not sit behind an unbounded telemetry backlog. Preserve job ownership/fences; no deployment-local timer is the authority.
- Retain 30-second visible workspace polling as an initial UI fallback. Propose active status checks around 60 seconds and performance reads around 5 minutes, adjusted for provider limits and empty-report backoff. These are engineering targets to validate under load, not guaranteed source freshness. Paused/historical campaigns can be checked less frequently; lifecycle changes trigger prioritized reads. Worker downtime/backlog must be visible even when the web API is healthy.
- Extend the existing refresh API instead of duplicating it. Return accepted/coalesced job identity, queued/running/completed/failed status, cooldown and latest observed evidence. A 202 response is not a completed network pull. Scope to campaign owner/admin; restrict diagnostic detail to current admins. Enforce durable per-campaign/account/actor budgets, not only an in-process HTTP limiter. Refresh never changes spend or clears a reconciliation hold.
- If adding socket/SSE notifications, send authorized versioned invalidations after database commit and refetch the scoped projection. Never trust a push event as finance authority. Test reconnect, stale/reordered messages and logout; polling remains a fallback. Do not introduce Redis or a second queue solely to obtain a live-looking animation.

### T3 — Connect truthful Encho outcomes (R7, subject to existing gates)

- Reuse canonical booking measurement ingestion, dedupe, correction sequence and scoped `bookingTruth()` as the base. Connect only accepted checkout/capture and current attribution/consent authorities. Remove the fabricated adapters under R1 first. Publishing or provider upload acknowledgements do not create bookings.
- Add a bounded tenant/campaign aggregate projection, not one expensive raw-event scan per card per poll. Record ingest watermark, coverage start, last accepted event/correction and completeness. Backfill/rebuild must be replayable without double-counting. No events with an unconnected/incomplete pipeline means “not measured/partial,” not confirmed zero.
- Define and version attribution window/model, supported campaign links, deduplication and cross-device/multi-channel limitations before reporting attribution as complete. Show provider-attributed conversions separately; do not sum them with canonical bookings or imply incremental booking lift. A refunded/cancelled order updates its outcomes rather than becoming another booking.
- Establish trustworthy first-party property-visit and inquiry events. Bind campaign/listing/host via server-validated attribution, use stable event/inquiry identity and existing authorized inbox threads, filter obvious bot/replay traffic and obey applicable consent/retention. A click is not a property visit and a message count is not a count of distinct qualified inquiries. Audit existing CRM before reuse; do not equate a legacy lead status with payment capture.
- Rename the ambiguous “Profile visits” card to the approved measured concept (proposed: “Property visits from ads”), or show a specific unconnected/unsupported state until supported. Define the metric before adding instrumentation. Host inquiry response stays in the Encho inbox; no external contact details enter alerts or analytics diagnostics.

### T4 — Host/admin monitoring experience (R5/R6/R7)

- Extend `workflow.project()`, studio types and shared panels together. Expose the proper window, data availability, source/freshness and safe action for each card; maintain currency precision. Independent lanes may update separately without hiding available status because bookings are blocked.
- Hosts receive clear status/timeline, latest valid performance, qualified Encho outcomes, funding/protection summaries, pause/help/refresh and in-app inquiry actions. They do not need provider portals or account terminology.
- Admins receive the same business truth plus worker heartbeat, oldest due observation, last success/error, attempt counts, next retry, safe provider reason/request IDs, account bindings and audited recovery. Diagnostic capture must be bounded, redacted and access-controlled; no raw response browser console or arbitrary provider query tool.
- Test desktop/mobile, accessible loading/error announcements without disruptive polling, stale views, logout/tenant switching, and identical totals for host/admin scope. Keep historical windows and reporting corrections visible; absence of evidence never gets a green LIVE badge.

### T5 — Acceptance and rollout (R8)

Tests must exercise the real provider adapters as well as injected engine fixtures: fresh zero/empty report, malformed row, multiple rows, wrong campaign/currency, future flight, account-midnight boundaries, 401/403/429/5xx, returned unknown status, slow status with successful report and vice versa, repeated DEAD jobs/rescheduling, more than 100 campaigns, manual/periodic coalescing, worker outage, stale control epochs, no duplicate pause, late provider corrections, booking/refund replay and cross-tenant access. Browser tests must verify queued-refresh versus completed observation and independent data-source explanations.

Record source-to-ingestion lag separately from ingestion-to-visible-UI latency. Load-test active status targets and control-job latency with the deployed worker count/provider quotas before choosing SLOs. Require bounded live readback parity for exact accounts/windows/currency and a confirmed safety-stop drill; provider/UI values may legitimately differ by retrieval time or attribution settings, which must be documented. Existing legal/checkout/provider acceptance gates remain; marketing dashboard completeness cannot be claimed while its lead/booking authorities are unconnected.

Impact: typed provider/engine/API contracts, proposed durable observation/health records and indexes, scoped outcome aggregates, scheduling semantics and both studio surfaces. Prepare migrations and ADR before implementation; preserve existing job/operation/financial identities. Roll out additively with old snapshots retained, compare old/new read projections, and keep spending disabled if new safety evidence is unaccepted. Rollback must preserve observation history and cannot turn unknown reports into zero or bypass gates. Do not silently rewrite ledger totals from reporting corrections.

## Verification performed in this review

- `vitest ... marketing_measurement.test.ts -t 'HARVO truthful telemetry normalization' --configLoader runner`: **17 passed**, 32 deliberately filtered tests skipped. Covers missing versus zero, units, source freshness and fractional attribution. It does not establish production dashboard wiring.
- `vitest ... safety_observation.test.ts --configLoader runner`: **7 passed** using the disposable local PostgreSQL fixture after sandbox shared-memory restrictions were lifted for that test command. Fixture ignores production database URLs. Covers independent local safety, stale fences, preserving pause/metrics and fair scheduling across failures/restarts. It does not prove actual provider pause or live spend safety.
- Initial default config-loader invocation could not write to the externally symlinked dependency cache; runner mode resolved it without editing dependencies. Initial sandboxed PostgreSQL run could not create shared memory; its skipped cases were not counted as passes.
- No new tests or production code were written. No live provider call, remote database action, migration, commit or deployment occurred. Documentation validation is recorded with the final review result.

**Disposition:** accept the telemetry UX and data-contract problem, refine all three Gemini findings as above, and add T1–T5 within R5–R8. Reject fabricated zeroes, fixed universal reporting SLAs, raw provider dumps, unsafe grace periods and claims that existing financial/protection controls alone certify readiness. Founder single-interface product intent is approved; proposed implementation details remain engineering plans, not completed features.

# M4 canonical measurement boundary

Updated 13 September 2026. Implemented source and isolated local verification; canonical checkout acceptance remains blocked. This module is deliberately disconnected from existing `CONFIRMED` booking crons, payment capture routes and live conversion uploads. Root runtime integration and all legal/provider gates remain separate.

## Interfaces and invariants

`MarketingMeasurementService(pool, { actorContext?, verifyBooking?, uploader?, now?, uploadTimeoutMs? })` exports `ingest(reference)`, `dispatch(limit)` and tenant-scoped `bookingTruth(campaignId, actor)`. Missing verification or upload ports fail closed. Writes also require an explicitly configured audited admin/service principal; no default actor ID is invented. A trusted verifier receives `{kind:'EVENT', reference}` or `{kind:'CURRENT', bookingId}` and a transaction client. It must read the accepted canonical booking/payment/consent authority and return the validated `VerifiedCanonicalBooking` contract. Legacy booking status, caller-supplied money and a deployment flag do not satisfy this port.

Evidence requires stable event, booking and unique order IDs; verified captured amount/currency and capture identity; host/property/campaign/provider identity; canonical acceptance and attribution references; explicit advertising measurement consent. No email, phone or raw click identifier is accepted into this contract. Provider adapters resolve attribution references only within their separately authorized boundary. Property/host/currency and observed remote campaign identity are checked at first recording; order attribution, original capture and currency are immutable. Events advance monotonically and remain append-only. Fulfillment changes stay truth without duplicating a purchase; partial refunds restate value and cancellation/full refund retract it. Captured funds remain recorded separately from cancellation state.

Ingestion uses a PostgreSQL booking advisory lock, unique order/booking/event constraints and immutable evidence. The conversion outbox has at most one purchase per provider/order. Corrections depend on accepted preceding uploads. Cancelled or consent-denied purchases are suppressed before sending. Current canonical consent is verified again immediately before dispatch. Newer events must be ingested before dispatch proceeds. Consent revocation after a provider has already accepted data requires a separate provider privacy/deletion process; this module does not mislabel suppression as remote deletion.

Dispatch commits `DISPATCHING` before calling an injected uploader. Each item has a stable operation ID/idempotency key and independently classified `ACCEPTED`, `REJECTED` or `UNKNOWN` result. Acceptance requires a safe provider receipt. Missing, duplicate, malformed or foreign results, transport timeout and network failures become unknown; there is no blanket uploaded flag. A lost final database commit remains `DISPATCHING`. Neither unknown nor abandoned dispatches are automatically retried. The added conversion delivery consumer can resolve known Google processing receipts read-only and repair abandoned dispatches from durable provider acknowledgements; claims without acknowledgements remain quarantined. See [conversion completion](CONVERSION_COMPLETION.md).

The additive migration is `src/migrations/011_harvo_marketing_measurement.sql`. It creates measurement projection, append-only events and conversion outbox tables, RLS owner reads/service writes, uniqueness and state constraints. It imports no legacy data. Rollback consists of disconnecting the new service and retaining audit evidence; do not drop financial or conversion history.

## Reporting truth

`normalizeMarketingTelemetry` accepts explicit provider/account timezone/report window, independent poll observation and provider data-as-of timestamps, measured values and exactly one declared spend unit. It preserves fractional provider attribution and converts money using exact integer arithmetic. Missing/invalid metrics remain `null`; only measured zero is zero. A missing poll timestamp makes the report unavailable. A valid observed report with no provider data-as-of timestamp can show measured values while explicitly retaining unknown freshness and settlement time. Poll completion is not proof that provider spend has settled. Output never claims immediate delivery or canonical bookings from provider attribution.

`bookingTruth` counts only recorded, verified canonical events. It explicitly reports `completeness: NOT_ESTABLISHED` rather than implying all marketplace bookings have been ingested. Host ownership is independently checked. Raw source evidence and totals are protected by tenant RLS; no guest-facing route is attached here.

## Verification and limits

The final focused run passed **49 tests** with real isolated PostgreSQL and injected upload responses. Focused strict TypeScript checking passed after the explicit service-principal and immutable capture/payload changes. Coverage includes concurrent ingestion and dispatch, append-only evidence, owner RLS, consent revocation, monotone adjustments, partial acceptance, malformed per-item results, hung uploader, abandoned writes and database commit failure. Verification includes property currency/capture immutability and conversion payload tamper rejection. No live conversion was sent, no canonical checkout was certified, and no booking lift was measured.

Actual provider adapters now implement strict consent mappings, destination binding, stable order/event identifiers, Data Manager purchase ingestion and diagnostics, Google v25 corrections and Meta v26 Purchase ingestion. Migration013 records provider delivery evidence. The combined boundary is locally verified by 96 tests; accepted canonical booking/consent resolver ports and live account eligibility remain unconnected gates. Unsupported Meta corrections are explicit remediation cases. The existing Google singleton remains disabled.

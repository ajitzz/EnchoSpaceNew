# HARVO settlement completion — impact analysis and implementation plan

Date: 2026-09-13. Authorized bounded task: close the paid-marketing final-cost accounting gap. This plan precedes code. It does not accept guest checkout, tax treatment, live ad delivery or remote database deployment.

## Verified current architecture and root cause

The existing MarketingFinanceService.reconcile method produces a balanced immutable journal, applies each immutable quote cost ceiling, calculates the snapshotted cost-plus markup and returns verified unused reserves. It requires a trusted verifySettlement callback, but runtime has no evidence-producing workflow for that callback. Provider reports and PAUSED status are not bill finality. Exposing that callback as an admin JSON passthrough would create an arbitrary balance-release endpoint.

## Primary provider evidence

- Google billing APIs require monthly invoicing: https://developers.google.com/google-ads/api/docs/billing/overview and https://developers.google.com/google-ads/api/docs/billing/invoice . Invoice retrieval is an authenticated read for a serving customer and billing setup, and consolidated invoices can include other customers.
- Google v25 invoices include campaign billable summaries through AccountBudgetSummary.campaign_summaries: https://developers.google.com/google-ads/api/reference/rpc/v25/Invoice.AccountBudgetSummary and https://developers.google.com/google-ads/api/reference/rpc/v25/Invoice.CampaignSummary . They also expose credits/corrections and replacements: https://developers.google.com/google-ads/api/reference/rpc/v25/Invoice . An issued invoice is evidence of billed costs, not a promise that no future adjustment can ever exist.
- Meta's official SDK exposes Business.get_business_invoices returning OmegaCustomerTrx: https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/business.py . This alone does not establish our account eligibility or a campaign-finality API. No invented Meta final-billing endpoint will be called.

## Scope and impact

Category: payment/accounting, database, security and operator API. New files: a settlement evidence/service module, bounded schemas and numbered migration 012_harvo_marketing_settlement.sql, scoped real PostgreSQL adversarial tests, and this document. Narrow financeService refactor will expose its existing settlement transaction to a trusted caller so campaign/proposal locks, audit and money journal commit together. Shared runtime/router/host/admin UI are integrated by the root agent using the published service interface. Existing quotes, captures and journals are unchanged; no historical balance import, remote migration or money movement is performed.

## Proposed solution and safety invariants

1. Administrators explicitly configured as financial operators upload actual bounded billing documents/receipts and supporting account/campaign billing exports or closure correspondence. The server computes their digest and retains immutable bytes/metadata in access-restricted tables. Provider identity, currency, billing period, document identity, provenance URL and original provider references are required. These remain manually sourced evidence unless an authenticated billing transport supplied them; uploads are not mislabelled API-verified.
2. A prepared closure binds one workflow campaign/revision/reservation/quote, every actual provider campaign and spending authorization, the exact document digests, complete cost allocation, explicit tax evidence and the configured accounting-close policy reference. A provider billing statement must cover the actual campaign flight; an official closure/billing export must identify the campaign. Shared invoices require explicit allocated amounts, and total allocations cannot exceed documentary totals. No inferred tax rate or cost-category mapping.
3. Two distinct currently persisted and configured financial administrators perform preparation and independent review. Approval includes an independent provider-portal verification reference and meaningful findings against the exact immutable proposal fingerprint. Self-approval, document uploader acting as independent reviewer, stale identity, rejected evidence or changed contents cannot authorize settlement. Rejection is append-only; a corrected proposal needs a new identity.
4. Closure requires the local campaign to be paused/ended, no pending or unknown provider mutation/job, exact current remote IDs and quoted revision, and an elapsed flight/billing period. Those are spending containment preconditions only. Actual billing documents plus explicit accounting-close evidence establish the close; zero metrics and PAUSED alone never do.
5. Settlement revalidates everything under the parent campaign lock and shares one transaction with the existing finance journal, proposal final state, document allocations and workflow audit. It must block later activation via finalized reservation status. Same-key replay returns the same result; a changed proposal or allocation is rejected. No automatic uncertain-reserve release.
6. Host costs are capped per immutable quoted cost line. Snapshotted 3–5% markup remains markup on defined costs, with no new tax assumptions. Later provider adjustments are separate evidence needing a compensating accounting review; they cannot silently debit the closed host account.

## Testing and rollback

Use fresh local PostgreSQL only. Test dual control and current role/configuration authority, bounded immutable documents, cross-campaign/account/currency/revision binding, complete authorization closure, invoice over-allocation, changed fingerprints, duplicate/concurrent settlement, pending/unknown provider operations, nonfinal billing windows, exact host cost ceilings, tax variance rejection, and balanced journal/account invariants. Inject no success fallback; no provider or payment mutations. Retain source/fixture distinctions.

Rollback means stop the new closure routes and preserve all documents, approvals, allocations and accounting history. Do not delete or rewrite finalized entries. Production activation additionally needs genuine accounting policy references, distinct human reviewers, provider-issued bills, actual billing account access and operational acceptance. No test receipt or assistant approval can supply those facts.

## Implemented service and integration contract

`MarketingSettlementService(pool, options)` requires named human `operatorIds`, a configured `policyReference`, server-owned provider account IDs, approved document portal origins and an authenticated read-only `verifyStopped(binding)` port. The latter is a containment check with a 15-second deadline and a five-minute observation freshness ceiling. It cannot establish billing finality. All admin actions also verify the operator's current persisted database role; commit rechecks both preparer and independent reviewer.

- `uploadDocument(actor, body, idempotencyKey)` retains 1 byte–5 MiB original PDF/CSV/JSON bytes, derives SHA-256, rejects credential-bearing source URLs and conflicting issued-document identities, and returns metadata with `source: MANUALLY_SOURCED_DOCUMENT` and `providerApiVerified: false`.
- `listDocuments(actor, {before?, search?})` returns `{documents, page: {nextCursor}}`, at most 30 records. `getDocument(actor, id)` returns metadata and binary `content`; the authenticated route serves an attachment, not a public asset.
- `list(actor, {before?, campaignBefore?, search?})` returns capabilities, `currentOperatorId`, up to 30 `eligibleCampaigns`, up to 30 `proposals`, and independent `page` / `campaignPage` cursors. Campaign results are candidates; preparing/committing revalidates every authoritative condition. Searches escape wildcard characters. Immutable creation-time/UUID keysets and supporting indexes retain access to historical records.
- `propose(actor, body, key)` binds the exact workflow/revision/reservation/quote and all provider operations/authorizations. It verifies billed flight coverage, exact campaign billing detail, account/currency, actual-cost codes, supporting cost invoices, taxes and up to 12 invoice allocations per line. An evidence bundle is at most 60 documents / 20 MiB.
- `get(actor, proposalId)` returns the exact proposal, independent review, and metadata for **every referenced document**, regardless of the current library page.
- `review(actor, proposalId, body)` requires exact proposal and document hashes, an independent verification reference and meaningful notes. The reviewer cannot be the preparer or any source-document uploader.
- `settle(actor, proposalId, {fingerprint}, key)` rereads provider stop evidence, takes campaign and document/account locks, validates both current administrators and immutable inputs, and commits the existing balanced journal, invoice allocations, proposal state and audit in one transaction. Response includes actual/charged cost, profit markup, platform overrun, separately remitted tax, returned available funds, currency and evidence. `providerAbsoluteFinality` remains **false**.
- `withdraw(actor, proposalId, fingerprint, reason)` terminates an unsettled proposal without deleting its documents or review; corrected evidence needs a new proposal.
- `hostSummary(actor, campaignId)` discloses only that host's status and committed financial result. Master invoices, other campaigns and reviewer evidence are not sent to hosts.

The public request schemas live in `settlementSchemas.ts`; none accepts an operator-controlled `final=true` or arbitrary ledger entries. All four new evidence tables force RLS and revoke PUBLIC privileges. Documents, reviews and allocations are immutable; terminal proposals cannot change.

## Host and administrator presentation

`components/marketing/SettlementWorkspace.tsx` exports `AdminSettlementWorkspace()` and `HostSettlementSummary({campaignId, currency, refreshKey?})`. The root dashboard mounts these components using the v2 settlement routes. Administrator preparation supports source document upload, provider identity, exact cost inputs, invoice splits, separate tax evidence and independent review. Original downloaded bytes are checked against the server-retained SHA-256 before a review checkbox becomes available; downloading does not automatically record approval. Review state resets when the operator, proposal fingerprint or status changes, and Refresh clears stale selected evidence. Search/pagination keeps earlier bills, campaigns and proposals accessible; preparation drafts survive evidence-library navigation. Reduced-motion styling and keyboard focus are provided.

The host summary labels money released to available funds separately from a refund to the original payment method. There are no fabricated invoice totals, assumed final zeros, API-certified labels for manual uploads, or guaranteed future provider finality.

## Verification record and remaining acceptance

First isolated PostgreSQL settlement + existing finance regression: **44/44 tests passed**, 2 files, 101.31 seconds. This includes eight concurrent preparation/commit attempts, platform overrun accounting, shared-invoice over-allocation, independent role revocation and an injected storage failure after money computation that rolls the entire transaction back. A later focused run passed **32/32 tests**, 2 files, 80.52 seconds, adding nonowner RLS, paginated historical records, canonical read projection, exact multi-invoice splits and pure browser amount/document-integrity boundaries. The credential-fragment URL rejection and its additional regression were added during that run; the consolidated suite must validate that final narrow change. Strict scoped TypeScript passed for the new service, schemas, UI and tests before the final narrow provenance regression.

This is an implemented **dual-control documentary accounting-close workflow**, not an automatic provider invoice importer. Google monthly-invoicing eligibility and live invoice API access have not been demonstrated for Encho. No permanent per-campaign finality promise is claimed for either provider. Human verification cannot cryptographically prove an uploaded document came from the provider; original portal access, a genuine approved accounting procedure and two accountable operators are deployment requirements. Corrected/replacement bills after closure require a separate evidence-backed compensating accounting review; this implementation does not automatically debit a host after close. No production document, provider mutation, payment, database migration or settlement was performed by these tests.

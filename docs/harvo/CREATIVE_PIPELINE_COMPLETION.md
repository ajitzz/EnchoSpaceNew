# HARVO — deterministic image preparation and immutable storage

Date: 13 September 2026. Scope: bounded image preparation/storage, not video transcoding, automatic creative optimization or derivative approval.

## Verified source and impact plan before implementation

`generateAdCrops` currently emits JPEG buffers but has no durable storage/review integration. `MarketingEngine.request` sends the selected approved source URL. `ProviderOperationStore` and `MetaAdProvider` bind publishing to approved listing media, with actual Meta video upload/status checks. `media_assets` has no derivative provenance/review contract. Replacing that URL with an unseen crop after the admin's approval would violate the current exact-asset boundary.

Add isolated image preparation and S3 storage modules. Preparation accepts server-read `ListingEvidence`, an explicitly owned/published listing, a selected approved IMAGE and confirmed advertising rights. Use the existing SSRF-protected approved-image loader. That loader produces a normalized JPEG, so provenance must name its checksum **normalized input checksum**, not claim it is the original stored object's checksum. Bound input bytes/pixels and local processing. Emit source-preserving, aspect-correct square, portrait, story and landscape JPEG canvases with neutral padding, no generated scenery, no crop or upscaling, stripped metadata, exact measured output dimensions and hashes. All outputs explicitly require review.

The actual S3 adapter receives an explicit client/bucket/CDN origin; it reads no environment or credentials. Use server-controlled content-addressed keys, conditional `If-None-Match: *` writes, explicit SHA-256 checksums and read-back checksum/length/provenance verification. Lost responses or existing keys permit read-only verification of the same object, never an overwrite or fabricated URL. An unverified write remains an explicit unknown storage outcome. The returned CDN URL is configured addressing, not evidence of CDN accessibility or provider acceptance.

No migration, original media change, provider substitution, runtime switch or auto-approval occurs. Root preserves original approved image/video publishing. The remaining integration must present actual variants to host/admin, capture explicit review of exact output bytes and persist immutable source/output/revision provenance before a derivative becomes an approved selectable provider asset. This work does not invent that authority or mark M5 complete.

Tests use real generated fixture pixels and injected S3 command responses, never real credentials, S3 writes or customer media. Cover owner/rights/source gates, dimensions, byte determinism, preserved source extent, no upscaling, malformed/animated/oversized content, metadata stripping, checksum/path binding, conditional writes, duplicate/lost write recovery and unknown outcomes. Rollback disconnects preparation/storage and retains any created immutable objects/evidence.

Primary implementation references: [sharp resize behavior](https://sharp.pixelplumbing.com/api-resize/), [S3 conditional/checksummed PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html), [S3 checksum-enabled HeadObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html). These support the transport/transform contract, not a claim of universal Meta placement acceptance.

## Exact integration contract and remaining work

`CampaignImagePreparer({allowedOrigins, loadImage?}).prepare(serverReadListing, sourceAssetId, hostActor, rightsConfirmed, formats?)` returns `{bytes, manifest, manifestHash}[]`. Supported format names are `SQUARE` (1080×1080), `PORTRAIT` (1080×1350), `STORY` (1080×1920) and `LANDSCAPE` (1200×628). These are review canvases, not a claim that every enabled provider placement accepts every image. The approved loader's normalized JPEG bytes are hashed separately from the output; orientation-aware measured input/output dimensions, source/listing identity, library versions and source-containing placement geometry are recorded. Each transform uses neutral padding, preserves the full source extent and does not enlarge it.

`ImmutableCreativeStorage({client, bucket, cdnOrigin, timeoutMs?}).put(preparedImage)` validates the actual buffer against its manifest, snapshots the caller's mutable data and conditionally stores both `.jpg` and complete provenance `.json` under `harvo/creatives/v1/{host}/{listing}/{sourceAsset}/{manifestHash}`. Both objects require authenticated checksum/length/type/provenance HEAD verification. A returned `STORED` result means those immutable S3 objects were read back; it explicitly carries `reviewRequired: true`, `providerApproved: false`, and `cdnAccessibilityVerified: false`. No configured CDN hostname is represented as a successful CDN request.

Deployment requires an explicit S3 client and bucket, narrowly scoped PutObject/GetObject/checksum access (and relevant KMS permissions for the selected encryption), an approved CDN origin mapping the same keys, and bucket policy preventing other writers from replacing/deleting the reviewed objects. Objects use conditional writes and immutable caching. Lost or conflicting write outcomes allow only exact read-back of the same keys. Neither a URL nor a checksum alone grants publication authority.

The next integration must: (1) call preparation only with freshly read owned listing/approved-source evidence and a bounded request/job budget, (2) retain the returned manifest and actual images for preview, (3) show each variant to the host and admin with its source identity and exact hash, (4) persist explicit approval bound to those bytes and the campaign revision, and (5) authorize provider selection only through that accepted derivative record while rechecking current source rights/publication. Client-submitted manifests cannot become trusted approval. Video/audio/frame review, transcoding and placement-specific video acceptance remain separate. Existing original-media publishing and real Meta video processing continue unchanged.

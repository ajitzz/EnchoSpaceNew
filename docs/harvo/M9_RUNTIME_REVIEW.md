# HARVO M9 — runtime security and recovery review

Date: 2026-09-13. Scope: independent review of marketing runtime, router, workflow, engine, jobs, authentication, configuration, media and legacy server integration. This is a bounded semantic review of these paths, not a completed line-by-line review of the entire project and not production or provider certification.

## Verified findings and changes

1. **Persisted account authority.** Legacy social moderation, global wallet inspection and inbox moderation included hardcoded email grants or trusted the role inside an older signed JWT. Email ownership/registration did not establish administrator authority. `resolvePersistedSession` now resolves account ID, role and email from the current users row on every authenticated request. Both authenticated middleware variants use it before setting RLS context. Removed all hardcoded email privilege exceptions. New v2 router independently rechecks the persisted account as before. Removed accounts fail closed; demotion takes effect on the next request. Phone-only accounts with a NULL email remain valid; the resolver omits the absent email instead of inventing one. The legacy guest fallback remains outside this marketing acceptance scope.

2. **Interrupted AI review.** The old workflow committed EVALUATING before media/AI I/O with no recoverable lease, so a process crash could permanently lock a campaign. Evaluation now stores a unique attempt identity and a database-time lease in the existing AI JSON evidence, has a 45-second absolute workflow deadline (bounded injected test override), and falls back to REQUIRES_REVIEW without a score or automatic approval. Recovery changes expired rows to PENDING_ADMIN with an append-only AI_REVIEW_RECOVERED event. Recovery is tenant-scoped, row-locked and bounded to 100 rows. Legacy EVALUATING rows without a lease recover after 75 seconds. The worker can sweep via `recoverExpiredEvaluations(actor)`; get/workspace/evaluate also recover relevant rows. A late response must match the exact attempt identity, not only revision/state. AI recovery never retries a provider mutation.

3. **Legacy organic social containment.** Social approvals previously generated random engagement and could return synthetic publication IDs when credentials were absent. Immediate publication happened before review audit persistence, with incomplete remote identity persistence, while a default-enabled scheduler could reclaim an ambiguous expired write. Approval now commits the current persisted administrator and exact post snapshot atomically and queues publication. The scheduler and publisher require explicit `HARVO_LEGACY_SOCIAL_PUBLISHING_ENABLED=true`. Only unchanged content approved by a reviewer who is still an administrator is eligible. An attempted or expired publication is not automatically replayed; failure requires operator reconciliation. Successful completion requires a real numeric remote media ID. Mock publication and random metrics were removed from this path. Ordinary social drafting/moderation remain available. This older organic publisher is still separate from the paid Meta v26 adapter and needs its own API/policy acceptance before opt-in; the flag is not a certification.

4. **Known local media overwrite path.** `/api/upload-local` previously accepted an unauthenticated caller filename and used overwrite-capable filesystem writes. That could change approved bytes while leaving the campaign's URL fingerprint unchanged. The authenticated upload-url endpoint now issues a ten-minute signed upload capability binding a current user, random server-generated key, exact content type and expiry. PUT verifies that capability and rechecks the persisted account, accepts no caller filename and uses exclusive file creation. Base64 local uploads also use random exclusive keys. Storage failure is an explicit failure, not a successful data URI. The existing uploadUrl/fileUrl/publicUrl response contract is preserved.

## Explicit remaining deployment gates and limits

- Campaign listing evidence fingerprints IDs, URLs and approval flags; it does not certify arbitrary mutable remote origins. Local uploads are immutable and S3 conditional signing/client support is now implemented and tested; the deployment must still verify bucket CORS/policies and older capability expiry. See S3_UPLOAD_IMMUTABILITY.md.
- Media DNS and HTTPS now share an absolute 15-second deadline. Three pure tests prove stalled DNS, continuous slow response data and combined DNS/download time are bounded. The workflow evaluation lease remains a separate state-recovery safeguard.
- Generic provider mutation fencing protects local state and prevents automatic overlapping replay. It cannot cancel an already transmitted external HTTP request. Unknown outcomes require provider-side containment and reconciliation; they do not authorize another mutation.
- Google/Meta observations are reporting observations, not settled final spend. Meta's configured ACTIVE state alone intentionally does not prove current delivery. Nonzero dated impressions establish past reported delivery only. A future flight may have no valid report window yet; missing/unavailable data must remain unknown, not fabricated zero or LIVE.
- Google OIDC verification uses verified RS256 certificates from Google's fixed endpoint, audience, issuer, expiration and signed account claims. The signed claim cannot grant a role. This review did not conduct a full production browser identity penetration test.
- The new admin/host workflows, queue fences and owned-row SQL were reviewed. Existing guest checkout/legal gates, all legacy social features and unrelated legacy routes are not accepted by this review.

## Verification evidence

`ops_security.test.ts` covers real PostgreSQL interruption recovery, timeout fallback, late-result fencing, tenant recovery scope, rate limit preservation, current account role checks, atomic social review, content/reviewer invalidation, attempted-write refusal, signed immutable local uploads and static server containment.

`engine_acceptance.test.ts` exercises 30 simultaneous HTTP requests per phase against real isolated PostgreSQL: one idempotent create, one revision winner with 29 conflicts, and tenant-scoped workspace reads with 30 campaign projections. Actual SQL statement count and latency are recorded in `M9_LOCAL_CONCURRENCY.json` when successful. Its separate pg_dump/pg_restore drill restores into another local database and verifies create identity, expired publish quarantine, forced RLS flags and the immutable audit trigger.

These tests inject authentication and AI/payment/provider boundaries where necessary. They never import application startup, read production database URLs, send ads or move money. Local timings are useful regression evidence, not production capacity promises.

### Completed local run

- All 13 `ops_security` tests and both `engine_acceptance` tests passed. Existing router and workflow/engine suites also passed during the initial regression run; its only failed case was a new test-source slicing assertion, subsequently corrected. Focused strict TypeScript checks passed for workflow, authentication helpers, immutable media helpers and the new tests.
- PostgreSQL 18.0 (Homebrew), 30 concurrent requests per phase: create p95 **1333 ms**, edit p95 **636 ms**, workspace p95 **452 ms** with **12 actual SQL statements per request** and 30 campaign projections. See the timestamped JSON artifact for p50/max/total values.
- Correctness: one persisted campaign for 30 identical create intents; one revision winner and 29 explicit conflicts; no cross-tenant workspace rows.
- Actual pg_dump/pg_restore drill: **3993 ms** in this run, same campaign on create replay, expired publication quarantined without another provider attempt, forced RLS and append-only audit trigger preserved.
- This measured local concurrency run does **not** support a claim of sub-200-ms responses at 30 concurrent workspace requests. Production capacity and latency require deployment-representative workloads, network, data volume, worker pressure and monitoring. A generic 15-second test deadline was insufficient on one busy local restore attempt; the restore test now has its own explicit 60-second bound rather than changing production timeouts.

### Conditional cloud media write follow-up

The separate scoped S3/client fix is now implemented: presigned PutObject uses If-None-Match `*` and signed Content-Type, a ten-minute capability and all five callers forward only the supported storage header. The signer no longer signs an empty-body checksum for unknown browser bytes. Twenty-five offline SDK/signature/client contract tests passed. See `S3_UPLOAD_IMMUTABILITY.md`. Bucket CORS, write/delete/copy restrictions, old capabilities and actual staging verification remain deployment gates; source code cannot certify those policies.

The later consolidated suite reran the load/restore test and overwrote `M9_LOCAL_CONCURRENCY.json` with its latest observation: workspace p95 740 ms under 30 concurrent requests, 12 statements/request, restore 4,302 ms. The earlier isolated 452 ms observation above remains historical; neither proves a 200 ms production service level.

Final consolidated 591-test run refreshed the JSON again: workspace p95 507 ms; restore/replay 1,726 ms. Use the timestamped M9_LOCAL_CONCURRENCY.json for the current observation. Earlier measurements above are historical local runs, not deployment SLAs.

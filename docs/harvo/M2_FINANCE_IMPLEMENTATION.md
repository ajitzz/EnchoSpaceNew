# HARVO M2 — Marketing financial foundation

13 September 2026. Implemented local foundation; real local PostgreSQL verification. No external payment, Neon migration, legal sign-off or live account clearance occurred.

## Scope and source evidence

Existing `doubleEntryLedgerService.ts` sums floating point amounts, tolerates a small imbalance, mixes account currencies in an audited balance query and permits cached legacy-wallet updates. Existing campaign contracts use the historical 15/85 gross split and do not demonstrate payment capture. The new service does not migrate, reprice or silently reuse those records.

Files: `src/lib/marketing/financeQuote.ts`, `financeService.ts`, `financeBridge.ts`, `refunds.ts`; additive migration `src/migrations/009_harvo_marketing_finance.sql`; isolated tests under `src/test/harvo/finance*.test.ts` and `workflow*.test.ts`.

## Commercial contract

The founder's denominator remains complete approved campaign costs C. The configured markup is basis points on C; the tested introductory policies use 300–500 basis points. There is no default policy, default rate or fixed 15% advertising fee. Booking commission is outside this service.

Every cost code in the versioned policy must appear exactly once, including explicit zeros. Codes identify provider media, service expense or nonrecoverable cost tax. Remittance tax is a distinct caller-supplied amount and is never treated as Encho profit or included twice in the cost base. The service requires cost-scope, accounting and tax reference fields. It does not substantiate those references or infer that a specialist has approved them; the composition root must establish that authority before enabling funding. Payment processing costs dependent on the amount collected must already have been solved by the approved pricing source.

Amounts are canonical decimal integer strings in minor units. Arithmetic uses BigInt with signed-64-bit bounds. The supported currency set is INR/USD, with no implicit conversion. The explicit supported policy is half-up rounding of the aggregate markup and platform absorption of cost overruns. Unsupported/missing policies fail closed. Financial policy changes create new immutable versions and never rewrite accepted quotes.

Each cost line in the accepted quote is a maximum chargeable to the host. Final verified costs above a line ceiling are recorded as platform overrun rather than increasing a host charge. The final markup is calculated on chargeable actual costs, with any unspent cost and related markup returned to available funds. Actual remittance tax cannot exceed its disclosed reserve; higher tax requires specialist review, not automatic extra collection. The settlement reports both recognized markup and realized campaign contribution after overrun; these can differ, and contribution can be negative. This is not company-wide net profit.

## API and trusted composition

`new MarketingFinanceService(pool, dependencies)` requires `actorContext: { id, role: 'host' | 'admin' | 'system' }` supplied by authenticated server code, never JSON from the host. Every service transaction uses transaction-local user/admin/RLS context; host calls also check their authenticated owner explicitly.

- `persistPolicy(policy, adminId)` checks the actual `users.role`, authenticated administrator identity and immutable policy hash. `currentPolicy(currency)` reads the most recently registered version for that currency.
- `quote(input, policy)` verifies campaign/property ownership and exact registered policy, snapshots the campaign revision, cost lines, markup, tax, expiry and fingerprint. Matching retries return the original snapshot; changed payloads reject. The idempotency fingerprint excludes only the retry key and creation timestamp.
- `recordVerifiedCapture(rawEvent)` requires `fundingEnabled: true`, a system/admin context and injected `verifyCapture`. A client `verified: true` does nothing. The verifier must authenticate the original gateway evidence, merchant/account, payment/order metadata and capture status. Returned capture data must match an existing quote's full amount/currency. Provider payment identity is globally unique within its merchant; multiple events for that payment never double-credit.
- A second distinct captured payment for the same quote is recorded as actual received money and freezes the host/currency funding account. The result sets `requiresReview: true`; orchestration must not treat it as new campaign readiness. Refund processing remains available while frozen. Unmatched/malformed verified events reject and must remain in the upstream durable event inbox for investigation.
- `reserve({ quoteId, hostId, idempotencyKey })` atomically moves captured available liability to campaign reservation liability. `reserveInTransaction(client, input)` provides the same owner validation and financial lock order inside an existing workflow transaction, so campaign validation, reservation and job creation can roll back together. A host/currency row lock serializes competing reservations/refunds/captures; database nonnegative constraints and journal reconciliation prevent double-spend.
- `authorizeSpending(client, input)` executes inside the caller's PostgreSQL transaction and workflow lock. It binds reservation, owner, campaign revision, provider account and exact media amount, checks remaining reservation, risk time and account freeze, then inserts one immutable authorization per reservation/provider. Existing permission/revision/AI/provider gates remain the workflow's responsibility. This function does not call an ad network or change money balances.
- `reconcile(evidence)` and `release(evidence)` require an injected trusted `verifySettlement`. Every provider authorization must be present in the verified closure set before settlement. No “pause requested” or local zero-spend assumption qualifies as provider finality. A cancellation is verified final zero-cost settlement. Finalization is atomic, immutable in the journal and idempotent; altered later settlement evidence requires a separately designed correction flow.
- `requestRefund` reserves available money in a refund-payable liability without making a gateway request. `requestRefundInTransaction` permits the workflow bridge to hold that liability, append the audit reason and enqueue the refund in the same transaction; a failed enqueue rolls back all three. `recordVerifiedRefund` requires trusted gateway verification, matching payment/account/amount and a final successful or failed result. Success clears the obligation against gateway clearing; verified failure restores available funds. Network uncertainty leaves the refund pending.
- `getSnapshot(campaignId, hostId)` returns owned quotes, reservations and host/currency balances under transaction-local context. Corporate gateway secrets and provider event payloads are not returned.

M2 applies a minimum 24-hour hold to every captured payment; it does not invent a verified-host exception. Reserved money inherits the current funding account risk-release time. A later risk decision cannot be fabricated from content approval. Approval route changes and worker orchestration are owned by the root implementation, not this isolated financial service.

Quote expiry limits payment acceptance, not the duration of an accepted risk hold. A matching payment captured within the quote acceptance period can be recorded by a delayed webhook and reserved after quote expiry. An expired quote with no such capture cannot claim unrelated available funds. Once the accepted capture is allocated for refund or refunded, it no longer revives expired terms using another campaign's money. A payment actually captured after expiry is still recorded as received cash, but freezes funding for acceptance review/refund instead of silently reviving the expired quote.

## Cancellation before any provider submission

A failed publication preflight can leave a wholly intact reservation without creating a provider operation. `WorkflowFinance.cancelBeforeProvider` closes that specific recovery gap: under the parent/workflow locks, it requires no provider transaction or entity, no legacy Meta transaction or external identity, no provider truth/telemetry, no spending authorization and no activation/control history. A failed or unknown provider claim still blocks this path. The finance service repeats the proof before releasing an intact `remaining = total` reservation under the host/currency and reservation locks.

The cancellation journal debits campaign reserved liability and credits host available liability for the full reserved amount. Its evidence explicitly records `NO_PROVIDER_SUBMISSION`; it does not impersonate an external billing statement or tax settlement. The same transaction marks the workflow cancelled, clears its pending job and advances publication job fences. An immutable audit binds the request key, revision and reason. An audit failure rolls back the money release and fencing together. Unfunded drafts can also be cancelled without a financial journal. Returning funds to the original payment remains a separate verified refund request; cancellation itself does not claim that an existing gateway checkout was voided or a bank refund completed.

## Original-payment refund adapter

`CampaignRefundGateway` requires a trusted admin/system actor and an existing financial refund obligation. `dispatch(refundRequestId, authorizeSend?)` verifies the original captured payment and configured recipient, then inserts one durable `marketing_finance_refund_operations` claim before sending. The worker passes its lease/fence guard to `authorizeSend`. An uncertain POST retains the refund payable and never causes an automatic second POST.

Stripe sends the exact requested minor amount against the original PaymentIntent with a stable refund idempotency key. Razorpay uses a fixed-origin HTTPS transport with a 15-second abort signal, bounded response size, no automatic retries, a unique receipt and `X-Refund-Idempotency`. The installed Razorpay SDK filters this header, so the narrow transport preserves the provider's documented contract directly.

Both providers require fresh GET readback matching the saved refund ID, original payment, amount, currency and Encho refund reference. Only `succeeded` (Stripe) or `processed` (Razorpay) settles a successful refund; confirmed terminal failures restore the held available funds. Pending results remain refund payable. `reconcile(refundRequestId)` reads known provider IDs and never issues a POST. A lost POST with no known refund ID requires explicit investigation; this adapter does not guess or search for an ID. A provider's processed status is provider evidence, not proof the customer's bank has displayed the credit.

Provider sources checked 13 September 2026: [Stripe refund creation](https://docs.stripe.com/api/refunds/create), [Razorpay refund creation](https://razorpay.com/docs/api/refunds/create-normal/), [Razorpay refund idempotency](https://razorpay.com/docs/api/refunds/normal-refunds-idempotent/). Live merchant behavior remains unverified. Gateway fees that a provider does not return are not silently deducted from the requested host refund; verified expense treatment and bank settlement remain accounting obligations.

## Host financial projection and bounded reads

`WorkflowFinance.snapshots(rows, actor)` binds campaign ID, owner and quote ID together, executes one tenant-scoped financial SELECT and returns projections for the current workspace page. It aggregates captured funds and pending/successful refunds, checks the account's available balance, freeze and risk time, and recognizes closed reservations. A refunded deposit, money allocated elsewhere or a settled reservation cannot display as spendable `CAPTURED`/`RESERVED` funding. `snapshot(row)` uses the same renderer; there is no separate financial truth formula for single-campaign and batch views.

The server supplies `funding.refundableMinor`. It is zero for an active reservation; otherwise it is bounded by available cash liability, the quote's unused captured amount after settlement and refunds, and the amount still refundable against one actual original payment. The host interface does not derive refund eligibility from a budget gauge. Refund requests lock the current workflow revision and quote, select the actual original capture, and bind the idempotency key to the amount and normalized immutable reason. Replaying the same request returns its existing obligation; changing the reason or amount requires a different request and renewed available-funds validation.

The 30-campaign local PostgreSQL workspace regression verifies **one financial SQL read** instead of a financial transaction per campaign. The original two transactions/ten statements became three transactions/fourteen statements when the parent added an explicit AI-lease recovery read; financial batching remains one transaction/four statements. Quote/capture and capture/refund indexes support the bounded joins. This query-count result is not a production latency SLA or a production load test.

## Database and invariants

All tables use the `marketing_finance_` prefix. New policies, quotes, captures, provider events, authorizations, journals and lines are append-only through database triggers. Journal entries balance exactly by currency and require at least two nonzero lines; deferred PostgreSQL constraint triggers check this at commit. Cached available/reserved/refund-pending totals must agree with the immutable journal at commit. Legacy `host_wallets` and `campaign_financial_contracts` are never changed by this service.

RLS is enabled and forced. Owner-bearing tables isolate `host_id`; journal lines inherit visible journals; authorizations inherit reservations; provider events are restricted to trusted processing; policy registration is admin-only. Service-level host ownership checks remain necessary even where a privileged PostgreSQL role bypasses RLS. Deployments must use the intended non-superuser role and authenticated server context rather than exposing configurable session variables to customers.

All eleven financial tables explicitly revoke privileges from `PUBLIC`, including refund operation records. Deployments must grant the intended application/worker roles explicitly. Refund operation status is mutable operational recovery state; the financial capture, quote, journal and audit evidence remains immutable. A configured actor ID or administrator approval never substitutes for a verified payment event.

The lock order is host/currency account before mutable reservation/refund rows in service money transactions. `authorizeSpending` receives an existing client and locks the reservation only. The workflow must hold its own campaign/revision authority and must not open nested service transactions while holding finance locks. A release racing authorization either sees the immutable authorization and requires its closure or finalizes the reservation first, causing authorization to fail.

## Validation and limits

Local validation: the parent consolidated run passed **545 tests in 21 suites**, including the financial quote/service/refund and workflow service/engine suites. The subsequent focused cancellation suite passed **16 tests** against real PostgreSQL, covering both sides of the provider-claim/cancellation race, stale worker refusal, concurrent idempotency, rejected historical claims, tenant/revision checks and audit rollback. Focused strict TypeScript compilation passed before the cancellation addition; final combined compilation remains part of the parent verification. PostgreSQL tests create a fresh Unix-socket-only local cluster and never read DATABASE_URL or import server startup.

Tests cover cost-plus arithmetic, explicit cost/tax scope, integer/range validation, immutable policy/quote identity, rejected unauthenticated funding, duplicate capture concurrency, double-payment quarantine, competing reservations, reservation retries, accepted capture across quote expiry, late-payment quarantine, caller transaction rollback, risk delay/revision/provider ceilings, provider closure, final-cost overrun absorption, refund competition/finality/replay, database journal/balance constraints, host isolation and FORCE RLS under an ordinary database role.

These are local accounting and authority tests, not evidence of live gateway capture/refund, bank settlement, chargeback recovery, production scale or legal acceptance. Source-level payment/refund adapters, durable jobs and prospective policy administration are being integrated in the parent HARVO execution track; their external account behavior, provider finality, tax approval and production migration remain acceptance gates. Later provider cost corrections, chargeback/dispute accounting and manual frozen-account release require explicit audited workflows; this service does not invent those outcomes.

Rollback is additive and non-destructive: disable financial entry points, preserve all journal/evidence records, and repair forward. Do not restore legacy synthetic funding, delete records or reprice accepted quotes.

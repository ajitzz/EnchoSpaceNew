# R4-01 participant notification mount — impact before code

**Source of truth and defect.** `createParticipantNotificationRouter` exposes the exact preferences/evidence API, and `ConversationNotifications` enforces participant RLS/catalog grants per call. The router is not mounted in `server.ts`; its only HTTP tests mount a synthetic Express fixture. Hosts cannot reach saved preferences or truthful notification evidence even when migration 039 and a restricted role are available.

**Narrow proposed repair.** Introduce an explicit participant-only PostgreSQL URL and a small runtime wrapper that creates a separate pool only when `CR1_CONVERSATION_NOTIFICATIONS_ENABLED=true`. Validate URL/TLS options before pool creation; never inherit the main application or notification-worker pool. Mount `/api/conversations/v1/notifications` under server-derived account authentication and the existing message mutation limiter. Keep feature-disabled or invalid configuration at 503. Reuse `createConversationNotificationRuntime`, `createParticipantNotificationRouter`, per-command `verifyNotificationPreferenceCatalog`, existing RLS and transaction code. Close the new pool on web shutdown. No schema, worker, money or external delivery operation changes.

**Impact.** Adds an API mount and one explicitly named secret requirement for later rollout. The route is account-only; it does not confer consent, claim SMS/email/push delivery, or bypass migration 037/039 catalog checks. Runtime configuration may be locally testable while deployed role/grant and privacy policy evidence remain missing. Existing inbox and read cursors are unchanged. Do not assign a migration number while 045/047 identity is unresolved.

**Validation and rollback.** A mounted-server test should fail before the mount (404) and pass afterward with 503 when disabled, 401 for unauthenticated callers, and no provider/database side effect. Separate config tests should reject unsafe remote SSL options and local URLs in production; restricted-role integration from existing notification preference suites remains controlling. Run targeted tests, Node 24 typecheck, scoped lint and diff check. Rollback by disabling the feature flag; keep the route's explicit unavailable result and never fall back to a broad ambient pool. Full R4-01 acceptance still requires channel/consent/privacy work and a named staging rollout.

**1 October local implementation/evidence.** An authenticated mounted HTTP test first failed with 404 before composition, then passed with a truthful 503 when the feature is disabled. The unauthenticated request is 401. `server.ts` now composes `createParticipantNotificationRouter` before the participant service router and closes its separately configured pool on shutdown. `src/server/conversations/participantNotificationRuntime.ts` accepts only `CR1_CONVERSATION_PARTICIPANT_DATABASE_URL` when the explicit feature flag is enabled; it rejects unsafe URL/TLS shapes and does not use the ambient application pool. Four focused suites passed **43/43** after this integration; Node 24 client/server typecheck, scoped lint and diff check exited 0. The read-only route inventory refresh matched 347 declarations and 370 expanded paths, and its six parser tests passed. These are local structural and HTTP checks, not deployed grants or external notification delivery.

**Independent defect discovered after mounting.** Antigravity's read-only review identified that `verifyNotificationPreferenceCatalog` examines only `current_user` for excess grants and overlooks reachable `NOINHERIT` roles, column-level `PUBLIC` ACLs and column-level `REFERENCES`. Codex reproduced the finding with disposable PostgreSQL: the focused authority suite passed 3 and failed 12, each false-positive readiness result returning `ready: true`. Treat the mounted preference path as unavailable for rollout until this catalog guard is repaired and the full adversarial authority suite passes. No privilege was changed on Neon. The bounded repair is assigned to Antigravity with source-file ownership; its output requires independent diff and test review before acceptance.

**Independent local repair check.** Antigravity's bounded one-file patch reuses `reachableRuntimeRolesSql`, checks all reachable function/table/column authority, and rejects PUBLIC column ACLs while preserving the current LOGIN's exact required grants. Codex inspected the diff and independently reran six targeted suites on disposable PostgreSQL/local fixtures: **83/83 passed**, including the 12 previously failing cases. Node 24 typecheck, scoped ESLint and diff check passed. The existing `verifyConversationCatalog`/`verifyRuntimeDatabaseAuthority` supplies the broader reachable-object-owner/CREATE/BYPASSRLS denial. Antigravity's final handoff reports the same one-file scope and local results, but is not release authority. Deployed restricted-role/branch verification remains outstanding; these local tests do not turn the notification path into a release-approved channel.

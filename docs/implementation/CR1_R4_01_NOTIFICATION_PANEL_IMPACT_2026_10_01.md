# R4-01 participant notification panel — impact before code

**Source and gap.** Migration 039, `ConversationNotifications` and the mounted participant routes define versioned in-app alert preferences and recipient-only evidence, but no Guest/Host UI calls those routes. `docs/implementation/CR1_P3_NOTIFICATION_PREFERENCES.md` explicitly requires an actor-fenced panel. External EMAIL/PUSH/SMS remain `NOT_CONFIGURED` and `NOT_RECORDED`; a socket hint is not device delivery.

**Narrow implementation.** Add a modular panel under the canonical Inbox for both Guest and Host views. Read strict shared Zod projections with `no-store`, bounded timeouts and authenticated fetch. Show in-app alert preference, version/source, and recipient-only recent intent evidence; label optional sound/visual alerts accurately. Keep the same command UUID and expected version when a PUT result is unknown; re-read canonical state before confirming a saved change. Ignore responses after account/token switches and abort in-flight reads. Do not store evidence, token or private content in browser persistence. Preserve Inbox socket refresh, unread counts, read acknowledgement and message content when optional alerts are muted. No new schema or external channel call.

**Security/compatibility.** Account identity comes from verified `useAuth`; the API independently derives it from JWT. Use the existing `X-Encho-Conversation-Command` header, rate limit and immutable receipt contract. Keep no-store and never display raw provider/queue payloads. A feature-disabled or catalog-unready response is a visible unavailable state, not zero notifications or proof of consent. Mounting is additive to the existing Inbox; rollback removes the panel and retains the existing routes/history.

**Validation.** Focused component tests must cover unavailable/read state, committed CAS save, ambiguous PUT retry with identical UUID, stale actor response rejection and truthful evidence labels. Run adjacent Inbox tests, typecheck, scoped lint and diff check. This local panel does not close R4-01 until the catalog false positives are repaired, real channel/consent/privacy policy is approved and staging roles/worker effects are verified.

**Evidence pagination repair impact before code:** The current panel replaces `evidence` on every `beforeId` response and offers no return-to-latest control once a page is present. That can make the recipient's newest intent evidence disappear after loading older records. Keep the canonical recipient-scoped API and cursor unchanged; merge older pages by notification ID in memory only, retain the newest page, and provide an explicit latest refresh. No database/API/security change. Focused regression: two-page evidence plus refresh after an added record; rollback is the panel-only UI change.

# R2-01 legacy campaign transition audit atomicity — impact note

**Source finding:** `server.ts` exports `transitionCampaignState`. It updates `host_marketing_campaigns.status`, then catches and logs a failed insert into `meta_publishing_events` and returns the new state. With its own PostgreSQL transaction, an SQL error also aborts the transaction; a later `COMMIT` can end as rollback while the function still reports success. With a caller-owned transaction, the helper suppresses the error and leaves the caller to discover a failed transaction later. Background reconciliation still calls this helper, although several public legacy paid routes are retired. An audit record is therefore not reliably atomic with the reported state result.

**Scope and authority:** Keep the canonical marketing v2 workflow and finance/outbox authority unchanged. Modify only this helper's event-write error boundary and a new focused regression; do not revive retired routes, alter state transitions, authorize provider spend or change a migration. The helper must reject when the audit insert fails. The caller owning a supplied transaction must roll it back; the helper's owned transaction already rolls back in its outer catch. A future full migration to canonical commands remains separate.

**Compatibility/security:** Success response shape and event schema are unchanged. An audit failure becomes a visible failed transition rather than a false success. Recovery callers may now surface a retriable error/incident instead of proceeding without evidence; inspect their catch/queue behavior before release. No admin override or provider state is inferred from a requested local transition.

**Validation:** First inject an event-write error through the helper's client interface and preserve the failing-before test. Then verify rejection with the same test, run relevant existing FSM/retirement tests through the sanitized Node 24 runner, inspect diff and run server typecheck. Actual PostgreSQL rollback and lost-COMMIT behavior still need a disposable-database integration receipt before card acceptance.

**Rollback/containment:** If downstream recovery cannot handle rejection, disable that legacy recovery path and reconcile its durable state. Do not restore silent audit failure or delete event history.

**Additional state-machine impact before code:** `VALID_TRANSITIONS` explicitly gives `cancelled` and `killed` no outgoing edges, but the same helper bypasses all edges when `actorType === 'admin'`. That permits an administrator-labelled caller to revive a terminal campaign without a new reviewed/funded revision. A narrow guard should make those two terminal states immutable for every actor while retaining existing administrator overrides among nonterminal states (the existing `pending_approval -> draft` test). Test both terminal states with an injected client and the existing FSM suite. No database/API schema changes; if a legacy recovery caller depends on resurrection, it must be contained and revised rather than silently spending again.

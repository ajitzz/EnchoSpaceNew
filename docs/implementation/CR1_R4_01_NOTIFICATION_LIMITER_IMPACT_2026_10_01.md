# R4-01 notification preference mutation limiter — impact before code

**Verified source.** `server.ts` passes the same IP-keyed, process-local `messageLimiter` to canonical chat mutations and the authenticated notification-preference PUT. A busy shared IP can exhaust the chat budget and block an unrelated account's preference change. Its 429 body is also outside the canonical public-error schema. The global `/api/` limiter is likewise IP/process-local and remains a separate broad capacity limit.

**Source of truth and narrow change.** Keep the existing participant notification router, authenticated account derivation, versioned preference command and restricted database runtime. Add a dedicated pre-command preference limiter with an injected atomic Redis counter, scoped by authenticated account ID and an isolated key namespace. Use an independent `CONVERSATION_NOTIFICATION_REDIS_REST_URL/TOKEN` identity; absent/unavailable counter fails closed for the optional preference mutation while Inbox messages/read/unread remain on their existing authority. The rate-limit response uses `RATE_LIMITED` and the same server-owned diagnostic context as the route. Wire only the preference PUT mount in `server.ts`; do not alter canonical chat limits or the database mutation. No new migration or public API path.

**Security and compatibility.** An authenticated actor is required before a counter key can be formed. One Redis Lua operation increments with TTL across instances; a local Map is not authority. Redis errors occur before any preference write and cannot be reported as a committed setting. This change can make preference writes unavailable until the dedicated Redis identity is configured; the UI must label that truthfully. Keys contain internal numeric actor IDs, no guest contact or message content. The existing global API IP limiter can still deny a shared NAT under heavy load; this slice does not claim that broader issue is solved.

**Validation.** First demonstrate failing server-composition behavior with a mounted test: exhaust chat limiter from a shared IP, then ensure another authenticated account's preference PUT is governed by its own counter and returns a canonical 429 only at its own threshold. Exercise absent Redis, Redis failure, invalid actor, cross-instance atomic count and TTL with disposable local Redis. Run adjacent notification API/component tests, Node 24 typecheck, scoped lint and diff check. No remote Redis/Neon/provider calls. Rollback restores the previous mount but also restores the documented cross-traffic defect; a safer emergency rollback is to disable optional preference writes while preserving Inbox.

**Actual mount compatibility before code:** The current server always mounts the notification router even when its restricted participant runtime is disabled, so authenticated GET and PUT must both say canonical `FEATURE_UNAVAILABLE` in that state. The dedicated Redis limiter should be mounted only when the participant runtime exists; an unconfigured limiter must never conceal a disabled feature as a Redis outage. Add a production-server mounted disabled-PUT regression, then wire the dedicated limiter for the enabled runtime only. The existing global API IP limiter remains a separate unresolved boundary and prevents a claim of full shared-NAT isolation. No database schema or provider effect changes.

**Final source-review questions before acceptance:** The corrected module still resolves the Redis store before validating its authenticated actor. With both inputs unavailable, it returns a dependency 503 instead of the intended 401, though the actual server authentication middleware currently rejects unauthenticated callers first. It also invokes `next()` inside the Redis `try` block; a synchronous downstream failure could be misreported as a Redis 503 after the protected handler has begun. Reproduce both at the mounted middleware boundary, then move identity validation before store resolution and call `next()` after the Redis error classification. These are narrow middleware changes with no route/schema/finance effect. Preserve the canonical 503 only for a pre-command store failure and never relabel a downstream/unknown result as a safe retry.

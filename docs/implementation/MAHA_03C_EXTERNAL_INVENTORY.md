## Admin business authorization writer — 2026-09-11

Impact/plan: add Admin-only POST /api/inventory-connections/:listingId/grants and /:listingId/grants/:grantId/revoke under the existing disabled inventory-mapping flag. Business authorization is separate from provider verification: neither endpoint creates attestations, mappings, observations or advertising/payment state. Owner ID is checked against the locked listing. Grant creation requires an authorization record reference, exact provider/connection/property tuple, explicit expiry in the future within 365 days and actor-scoped UUID retry key. The lifetime cap is an operational safety bound, not a provider/legal SLA. No secrets belong in identifiers or authorization references.

Grant and revocation records are themselves append-only audit records with actor attribution. Listing locks serialize them with mapping verification. Cross-listing grants additionally acquire a resource advisory lock and reject existing unrevoked/unexpired provider-property authorization before insert. Exact retries return the same grant ID without claiming the grant remains current or provider-verified; changed requests conflict. Repeated revocation preserves the original actor/reason; only identical retries succeed. Expired/legacy grants remain immutable. The staged inventory_grant_idempotency migration adds nullable retry metadata for legacy compatibility and a unique actor/key index; new route always supplies both fields. No database was migrated in this slice.

Eight injected route tests cover role/flag gates, ownership/lifetime conflicts, duplicate grants, identical/conflicting retries, revocation retention, rollback and rejection of injected providerVerified. Full isolated suite 242 passed / 22 opt-in PG skipped; scoped lint passed. Provider integration direction/access and real attestation ingestion remain unresolved; no provider fact is invented. No Admin UI controls added yet. Rollback disables inventory flag and retains all audit records, never deletes authorization history.

Next: isolated writer migration/concurrency acceptance, then an authenticated Admin read/status workflow and trusted provider-attestation ingestion after integration/access validation. ## Mapping lifecycle implementation — 2026-09-11

Impact/plan: separate immutable mappings/events from a replaceable current pointer. Under the listing lock, authenticate owner/Admin reads and Admin-only writes, validate canonical room membership, exact-version and actor-scoped retry keys, and require a trusted server registry verification of the exact provider binding/owner before creation. Pointer replacement or removal and immutable event insertion commit together; failures roll back. Database uniqueness prevents two current rooms using the same provider/connection/property/room tuple. Revocation retains evidence. No provider calls inside locks: the verifier contract is a transactional registry lookup, not a network adapter. No verifier is installed, so actual creation fails closed.

Implemented in src/server/externalInventoryMappings.ts and the additional staged 20260911_external_inventory_lifecycle.sql migration. Routes GET/PUT/DELETE /api/inventory-mappings/:listingId/rooms/:roomId are mounted behind INVENTORY_MAPPING_ENABLED=true (default off). PUT/DELETE require version (null for no history), UUID requestKey and reason; PUT also requires the binding. Responses expose current mapping ID/version and explicitly deny checkout and advertising authorization. Exact retries return the original operation version plus current state identifiers without repeating mutation. New properties/rooms are not created by these routes. Existing Host/guest source declarations and booking gates remain unchanged; read-only status UI is next.

Security/performance/compatibility risks: canonical provider connection identity and fresh ownership attestations must be supplied by a real server registry before creation is enabled. Ownership transfers and connection revocation need integration with that registry. Application-role arbitrary SQL remains outside the RLS guarantee. Listing-level locks serialize room mappings; unique indexes protect cross-listing provider claims. Evidence append-only history is not pruned. The new migration is not automatically applied or production-compatible merely because minimal fixtures pass. Rollback: disable the flag, retain mapping/evidence/events; never restore revoked pointers blindly.

Verification: 12 injected lifecycle regressions pass within the full 222-test isolated run (16 opt-in PG tests skipped). Nine real PostgreSQL 18 tests passed in a new private /private/tmp/encho-inventory-test.VCm85e cluster, applying both migrations; include concurrent stale versions, retry replay, unique provider assignment rollback, retained revocation history and audit RLS. Cluster stopped and retained. Frontend/server build passed; scoped lint passed. No Neon, provider or payment operations. Next: read-only Host/Admin status UI and its authorization/browser tests, then real server connection registry and provider attestation/observation ingestion; reservation propagation remains mandatory before checkout.

Source finding: inventory_source is a reviewed declaration, while no server-owned provider mapping or dated observation exists. A host claiming external_sync must never establish synchronization or checkout eligibility.

Plan and impact: add a separate server-only, provider-neutral contract and an unapplied migration. Bind evidence to an immutable mapping revision containing the actual listing/room, provider, connection, provider property and provider room identities. Require a complete snapshot for the requested half-open date interval, exact matching identity, finite nonnegative integer stock, and both provider observation and server receipt timestamps. Missing, mismatched, stale, future or incomplete evidence is unknown. No HTTP endpoint, worker, host-writable verification field, existing API/schema mutation, provider call or checkout/advertising authorization is introduced. Host/Admin/guest retain existing unknown/external-source labels and fail-closed checkout.

The adapter returns untrusted data and must normalize a genuine full provider snapshot, not represent an omitted delta as zero or unchanged stock. The server validates its output. Five minutes is a conservative maximum evidence age for this staged projection, not a claim about any provider SLA. Even fresh positive evidence authorizes neither checkout nor delivery: inventory reservation propagation, double-counting semantics and external contention must be resolved first.

Mapping revisions and evidence are append-only; replacement mappings invalidate prior evidence by identity. A future service must lock the listing, check ownership and canonical room membership, authorize the operator, validate provider ownership, audit mapping/revocation, and transactionally choose the current revision. No active-mapping selection or write service exists yet. Connection IDs are opaque internal references, never credentials. Migration RLS permits owner SELECT through the listing relationship, with writes limited to the existing server-selected transaction-local bypass. This assumes callers cannot run arbitrary SQL/set bypass; dedicated database roles/grants must be validated before deployment.

Tests: isolated pure contract/adapter regressions, application/server compilation, scoped lint. Database constraints, application-role RLS and migration compatibility require an isolated PostgreSQL run before application. Performance is bounded to at most 365 daily rows per snapshot. No network latency or runtime UI performance claim.

Rollback: leave flags disabled; remove only these unused additions if necessary. If eventually applied, preserve immutable evidence and revoke writer access instead of deleting history. No backfill or migration execution in this task.

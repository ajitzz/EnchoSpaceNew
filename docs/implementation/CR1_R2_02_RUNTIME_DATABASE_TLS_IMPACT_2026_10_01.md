# R2-02 runtime database TLS — impact before code

**Verified source and installed-library behavior.** `server.ts` creates the write pool with `ssl: { rejectUnauthorized: false }` for any remote URL and clones it for the read pool. The installed `pg@8` / `pg-connection-string@2.14` parser overrides that option when the URL carries `sslmode=require` and currently treats `require` as certificate-verifying `verify-full`. The locally configured primary `.env` URL has a remote target and `sslmode=require`; no credential bytes were printed. A fake-URL, no-network check of the installed parser showed `sslmode=require` yields an effective empty SSL options object, while an absent mode or `no-verify` retains `rejectUnauthorized: false`. The package itself warns that this `require` alias changes to weaker libpq semantics in the next major version. This is a latent runtime security/configuration failure, not proof of a current TLS interception.

**Proposed narrow change.** Centralize a strictly typed remote-PostgreSQL URL validator used by write/read pools and the dedicated marketing worker. Require `sslmode=verify-full` for remote targets and reject `no-verify`, `disable`, absent mode and libpq compatibility that downgrades verification. Keep explicit loopback fixtures and the sanitized test runner working. Remove `rejectUnauthorized: false` rather than assuming a URL parser will override it. Do not expose URL, username or password in errors/logs. Separately verify migration preflight/runtime parity without contacting Neon during unit tests.

**Impact and validation.** Affects database pool construction in `server.ts`, `src/server/marketing/worker.ts` and possibly the older `worker.ts`; no schema/API/UI changes. Tests should instantiate fake URLs and installed `pg` connection parameters without connecting, exercise primary/read-replica fallbacks, reject downgrade strings and protect existing local fixtures. Run relevant focused suites, server/client typecheck, scoped lint and offline packaging. A deployment with only `sslmode=require` would need an explicit approved secret configuration change to `verify-full` before activating a strict gate; do not silently rewrite the production URL or disable verification. Rollback cannot re-enable non-verifying TLS.

**Current bounded worker assignment and broader entrypoint inventory (2026-10-01).** Antigravity was assigned only the primary `server.ts` write/read pools and `src/server/marketing/worker.ts`, plus a pure helper and tests. Independent source inspection also found separate pool constructors in `worker.ts`, `src/server/marketing/adtechWorker.ts`, and `src/server/marketing/operator.ts`. They remain in the TLS review inventory; a passing patch for the assigned paths cannot establish runtime-wide coverage. The currently installed parser treats `sslmode=require` as certificate-verifying, but it warns that its alias can change in the next major version. For a compatible repair, normalize `require` only inside a validated pool configuration to explicit verification, while preserving the configured target and rejecting downgrade modes. Any code change must prove that the actual `pg` connection parameters verify certificates and that read replicas are validated independently. This refines the earlier strict-gate proposal without claiming the deployed secret has been updated.

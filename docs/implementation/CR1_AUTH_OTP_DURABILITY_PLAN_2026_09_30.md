# CR1 phone OTP durability and abuse-control plan — 30 September 2026

**Status:** source repair implemented in the dirty primary checkout and locally tested; `READY_FOR_REVIEW`, not a deployed or accepted phone sign-in path. Existing email/Google sign-in contracts remain distinct. No named staging Redis authority or deployed multi-instance receipt exists.

## Proven defect

`server.ts` stores the six-digit challenge in a process-local `Map` and uses an in-memory IP limiter. In a serverless or horizontally scaled deployment, `/send` and `/verify` can hit different instances; attempts, one-time consumption and rate limits are then inconsistent. The current OTP response projection was narrowed separately, but that does not repair challenge durability. No shared OTP store, cross-instance attack test or deployed provider receipt has been produced.

## Proposed service boundary

**Implementation impact note (before code, 30 September):** The source-of-truth challenge moves from `server.ts`'s process `Map` to a dedicated Redis keyspace through atomic Lua commands. Affected paths are a new `src/server/auth/phoneOtpChallenge.ts`, the two existing HTTP routes in `server.ts`, and focused challenge/HTTP tests; no PostgreSQL schema, finance, provider, workforce or guest property contract changes. The public response remains a minimal identity. A configured shared store and keyed digest are required; absent/invalid configuration or Redis failure returns 503 rather than falling back to memory. The existing local IP limiter remains defense in depth while shared per-phone/IP counters enforce cross-instance limits. Rollback is route containment (503 or previously available alternative sign-in), never restoration of a production process-local OTP authority. Current phone strings are stored in `users` without a verified canonical uniqueness migration; the first code slice will normalize challenge/delivery addressing but preserve existing persisted raw phone lookup to avoid silently merging accounts. This legacy identity-format gap remains a separate release criterion.

1. Extract `PhoneOtpService` behind a small `OtpChallengePort` and a separately injected delivery port. Keep the HTTP adapter limited to Zod-validated phone/code/name, bounded response messages and public identity projection. Normalize phone numbers to a documented canonical format before indexing or sending; do not silently reinterpret international numbers as Indian numbers.
2. Use a **dedicated, configured shared Redis namespace** for short-lived challenges and per-phone/per-IP issue and verification counters. Store a keyed digest of the code and normalized phone, never plaintext OTP, phone number or provider token in a Redis key, audit event or application log. Require a separate high-entropy OTP MAC key; do not reuse browser JWTs as Redis secrets. Upstash's TypeScript SDK documents server-side atomic `EVAL` and expiry-capable `SET` operations: [EVAL](https://upstash.com/docs/redis/sdks/ts/commands/scripts/eval), [SET](https://upstash.com/docs/redis/sdks/ts/commands/string/set). Verify the installed SDK's exact signatures and the deployed Redis consistency topology before coding.
3. One atomic issue operation must enforce rolling limits, replace only the same phone's current challenge, assign an expiry and return a challenge generation. A failed delivery may revoke only its own generation; a concurrent newer challenge must survive. On ambiguous delivery, report unknown/unavailable without claiming delivery. Verification must atomically compare, count attempts, consume exactly once on success and expire/lock after the bounded failure count. A Redis/network error fails closed; it never falls back to a process-local `Map` in production.
4. Keep the existing persisted-user lookup and public response after durable consumption. A database failure after OTP consumption must not issue a session; the user can request a new code. Session creation and user enrollment need separate canonical uniqueness/error handling, not a retry that reuses a consumed OTP.
5. No migration number is allocated while the deployed 045/047 history is unresolved. Redis avoids changing the Postgres schema for this challenge store, but live Redis credentials and scoped deployment policy still need an explicit environment receipt. The existing `.env` lists Upstash variable names, but it is the primary environment and has not been used for this local plan or test.

## Required adversarial acceptance tests

- Two independent service instances share one fake/ephemeral Redis authority: send on A, verify on B, one winner under concurrent verify; replay denied.
- Invalid/expired code, wrong phone, code brute force, issue flooding across IPs and phones, counter TTL, malformed/Unicode input and clock boundary fail safely without leaking whether an account exists.
- Provider delivery failure versus concurrent issue cannot erase the newer challenge. Lost delivery acknowledgement and Redis outage return a truthful failure/unknown state; no success response or JWT is minted.
- Restricted local HTTP tests prove no password hash, wallet, Google linkage, challenge digest, key or raw provider response reaches the browser. Cross-instance tests use isolated local backing service; no live WhatsApp request is made.
- Node 24 targeted tests, typecheck, lint and offline build pass. Named staging must then prove deployed shared-store configuration, rate controls and legitimate sign-in across separate instances before this path can count toward production readiness.

## Rollout and rollback

Feature-flag phone OTP behind shared-store readiness. Deploy code with the path failing closed until the dedicated secret and Redis namespace are configured in named staging. Exercise cross-instance sign-in and outage behavior there before production activation. Rollback the feature flag or route to unavailable state if the store/transport fails; never re-enable the process-local Map as a production fallback. Preserve email/Google authentication and avoid sending a real OTP during local verification.

## Local implementation and review checkpoint

The current `server.ts` HTTP routes call `RedisPhoneOtpChallenge` instead of the process-local `Map`. `src/server/auth/phoneOtpChallenge.ts` uses three atomic Redis Lua operations for issue, consume and generation-fenced revoke, HMAC-keyed phone/IP/code digests, five-minute challenge expiry, shared issue/IP counters, and bounded wrong-code attempts. Both routes return 503 without shared-store configuration or after a store exception. A provider delivery failure revokes only the failed generation. The existing public user projection remains narrowed to identity fields. This patch is **local source evidence**, not proof that Upstash executed these scripts in staging or that WhatsApp accepted a real authentication message.

**30 September review correction:** An independent Antigravity read-only review found that the first patch combined unrelated IP and phone keys in one Lua `EVAL`, treated an ambiguous WhatsApp response as a definite rejection, used free-form OTP messaging, and lacked a consumer-admin role fence. The clustered-Redis claim was broader than the available Upstash evidence, but the implementation now separates the single-key IP counter from same-hash-tag phone operations. It uses a configured WhatsApp Authentication copy-code template, keeps an unknown-delivery challenge usable, and refuses an admin-role JWT from consumer phone OTP. The IP threshold is now 100 sends/300 verifications per hour as coarse shared abuse control, with five issues per phone per hour and four wrong codes per challenge. These are provisional engineering controls, not a reviewed abuse policy. See [independent disposition](../audits/ANTIGRAVITY_OTP_REVIEW_2026_09_30.md).

**Mounted-UI follow-up impact before code:** `AuthModal` changes to code entry only on HTTP 200, so a code arriving after an ambiguous provider response cannot be entered even though Redis preserves it. Add an explicit `deliveryStatus` to the two send responses, keep 503 for unknown, and let only that exact response open code entry with a warning. A successful Graph API acknowledgement must not be phrased as handset delivery. No database, payment, campaign or workforce contract changes. Test both HTTP response semantics and mounted modal behavior; rollback by disabling phone OTP, not by claiming the message was delivered.

Under a credential-free Node 24 test environment the **four focused suites passed 19/19** after three additional HTTP regressions for four wrong codes, the per-phone send budget and concurrent one-winner verification. A later modal/HTTP rerun passed 10/10 after adding manual code entry for a lost client response. The first modal run failed 2/2 because its inputs had visually present labels without accessible associations; `htmlFor`/`id` links were added and the repaired suite passed. A disposable local Redis 8.10.2 instance executed the actual Lua issue/verify/revoke/counter commands and passed cross-instance one-winner consumption, generation fencing, attempt limits, send limits and key expiry assertions; the command exits 0 and destroys its private socket/database. Client/server `npm run typecheck`, scoped ESLint and `git diff --check` exited 0 after the final UI/test change. The earlier HTTP rerun failed because pg-mem lacked `regexp_replace`; the test fixture now implements only that exact expression, and the repaired test passed. These results do not prove Upstash REST execution, distributed deployment, PostgreSQL RLS or live WhatsApp delivery. No approved template status or staged phone-send receipt exists.

**Open identity/performance gaps:** `users.phone` is unique only on its raw string. The route scans `regexp_replace(phone, ...)` for punctuated legacy values and fails closed for ambiguous or digit-only legacy matches, but no expression index/canonical uniqueness constraint exists while applied migrations 045/047 remain unreconciled. Digit-only historical accounts and heterogeneous country-code formats require a reviewed identity migration; the current lookup cannot establish their equivalence. A full-table expression scan is not a scaled identity design. The added admin-role fence prevents this OTP route from issuing a privileged JWT, but other legacy consumer-admin authentication routes still need separate workforce/consumer authority review. No new migration number is allocated here.

**1 October identity correction:** A second independent Antigravity read-only review found that the non-Indian lookup supplied `''` as a third candidate and therefore matched blank legacy phone rows; it also found that public registration could pre-claim the predictable generated phone email. Two HTTP tests reproduced the failures (2 failed / 8 passed) before the fix. The current route builds only nonempty phone candidates and stores `email=NULL` for a new phone-only account; the consumer session schema accepts that honest nullable value, `/api/auth/me` retains it, and the mobile profile displays the phone instead. The repaired four focused suites pass 21/21, Node 24 client/server typecheck, scoped ESLint and diff check exit 0. [Exact impact and rollback](CR1_OTP_IDENTITY_CORRECTION_IMPACT_2026_10_01.md). The third read-only review is in progress; no full R1-03 or production acceptance follows. The legacy full-table normalization scan, canonical index, deployed email-nullability check and stranded-code experience for a deliberately fail-closed legacy collision remain open.

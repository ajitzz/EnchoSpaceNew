# R1-03 auth-expiry inquiry preservation — impact note

**Scope:** Frontend offline-intent authority, not a new CRM or payment path. `AuthContext` currently treats `/api/auth/me` 401/403 as explicit logout and calls `clearActorScopedOfflineData`; that increments the actor replay fence and deletes queued inquiry `clientEventId` before same-actor reauthentication. The production-built browser fixture only rejected message submission, never `/api/auth/me`, so the accepted-looking token-expiry case missed this path.

**Change:** Keep signed-out UI and remove credentials on rejected authentication, but mark the former actor as expired before cross-tab storage events and preserve only its actor-scoped, credential-free offline queue for same-actor reauthentication. Explicit logout and account switch still revoke the fence and purge private actor data. A different actor signing in after expiry revokes the expired actor before new credentials are installed. Legacy Workbox queue stays retired. The pending inquiry is never replayed without fresh credentials and the same actor identity; the existing server idempotency key remains unchanged.

**Affected surfaces:** `components/AuthContext.tsx`, `components/InboxPage.tsx`, `lib/syncService.ts`, the production-built browser fixture/test in `src/test/harvo/cr1_offline_worker_lifecycle.test.ts`, and focused queue/Inbox tests. No database, API shape, provider, finance or migration changes. Private cached UI remains hidden after expiry. After same-actor authentication, the Inbox reads only that actor's exact-thread queued messages, renders them as awaiting confirmation, and converges on the canonical event UUID. Actor-scoped offline content persists in browser storage until replay or explicit purge, a deliberate availability/privacy tradeoff that needs product retention review before release.

**Validation:** First reproduce queue deletion with an actual `/api/auth/me` 401 on reload. Then prove same-actor pending identity survives, appears in the mounted Inbox and automatically replays once with fresh credentials; different-actor login and explicit logout purge it. The final focused actor-scoped sync, Inbox and production-built browser suites, typecheck and scoped lint must pass after all changes. The local fixture does not prove arbitrary already-running legacy workers can be neutralized before update.

**Rollback:** Revert only this scoped source/test diff after capturing current working-tree identity; do not reset the checkout or erase unrelated edits. Containment if this policy is rejected is online-only inquiry submission with explicit pending/unknown notice, not silent queue deletion.

## Follow-up impact before code: auth response minimization and runtime identity validation

Tests: local HTTP OTP response with a seeded sensitive row and a stubbed transport; production-built browser fixture with malformed `/me`; targeted typecheck, lint and diff check. Rollback only these scoped auth changes after preserving the working-tree diff, and leave protected views masked until a safe identity response exists. No external WhatsApp, Neon or provider call is authorized for this test.

## Follow-up impact before code: per-command replay acknowledgement

**Source of truth and root cause:** IndexedDB stores actor-scoped offline commands; the server's canonical event UUID/idempotency contract resolves an uncertain HTTP outcome. `processOfflineQueue()` currently accumulates completed IDs in process memory and deletes them only after the whole batch. Antigravity's isolated test showed a first successful command remains durable while the second command is in flight. A tab interruption in that window permits an avoidable second request. The test's overlapping-executor simulation is evidence of that window, not proof of exactly-once HTTP delivery: a crash between a 200 response and the subsequent IndexedDB write can still retry, so server idempotency remains mandatory.

**Change and impact:** Acknowledge each definitely completed, rejected or retired command immediately using the existing atomic actor-key update. Keep unknown outcomes and retryable statuses queued. If an acknowledgement write fails, stop the current batch rather than dispatching later commands. Emit the browser committed event only after acknowledgement and only under the still-verified actor session; the Inbox still reconciles against canonical server history. Scope is `lib/syncService.ts` and its focused actor-scoped tests. No API, schema, provider, payment, IAM or migration change. A public entry in the queue never acquires authority from local storage alone.

**Validation and rollback:** Add a failing-before two-intent test that holds item 2 in flight and requires item 1 to be absent from the durable queue at that point, plus a durable-write failure regression. Run the focused sync, mounted Inbox and production-built browser suites, Node 24 typecheck/lint and diff check. Roll back this narrow queue change if actor fencing or event delivery regresses; retain server UUID idempotency and unknown-outcome reconciliation in every case.

**Local result:** The current-tree two-intent test failed before repair because both event UUIDs remained in IndexedDB while the second request was in flight (39 passed, 1 failed). The loop now acknowledges each definite result before the next dispatch and exits when the acknowledgement write fails. The unknown-outcome second item remains queued. **1 October release-blocking source finding — pre-upgrade worker credential after consumer logout:** Current `server.ts` signs consumer JWTs for seven days and `authenticateToken` verifies the signature then calls `resolvePersistedSession`, which reads the current `users` row but no token/session revocation state. `AuthContext.logout` revokes only the browser replay grant, clears browser/private state and removes local storage; no consumer logout API exists in the current router scan. A legacy service worker that already captured the bearer token before an update can therefore still present that token while it remains valid, even after browser logout. The production-built browser fixture intentionally denies background sync until the replacement takes control; its passing old-queue purge tests do not disprove an already-dispatched old-worker request. This is a source-level risk finding, not a demonstrated paid/provider effect.

**Required design/release work, not yet implemented:** Introduce durable server-side consumer session identity and revocation with fresh authorization on protected requests; keep workforce sessions on their separate authority. For an installed old client that cannot call a new logout endpoint, the rollout must invalidate legacy bearer tokens (for example via a controlled signing-key cutover) and verify that old-worker replay receives 401. Design the token/session storage and migration only after the applied 045/047 history is reconciled; do not repurpose an unrelated column or invent an in-memory blacklist. Add an actual production-built old-worker dispatch plus disposable server authentication test across logout/account switch, restart and token expiry.

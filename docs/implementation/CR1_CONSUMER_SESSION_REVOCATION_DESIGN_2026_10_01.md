# CR1 R1-03 consumer-session revocation design — review candidate

**Status:** Source-verified risk and implementation proposal, not an approved migration, released feature or R1-03 acceptance. The current checkout signs seven-day consumer JWTs and authenticates them against only the current `users` row. `AuthContext.logout()` clears browser state without a server call. A token already held by an older service worker therefore remains valid until expiry while the user row exists. The production-built browser tests cover replacement-worker purge, not a pre-upgrade worker already dispatching to the server.

## Impact before code

| Boundary | Proposed change | Compatibility and failure behavior |
|---|---|---|
| `server.ts` consumer sign-in and `authenticateToken` / `optionalAuthenticateToken` | Issue a cryptographically random per-session identifier; persist only its digest with account ID, issue/expiry, status and version. Sign a short-lived access JWT containing the opaque identifier and a new contract version; issue a separately rotated refresh credential whose digest alone is stored. Recheck the active session and current user on every protected request. | Reject a signed token with missing/unknown/revoked session; database uncertainty returns 503 before protected effects, not a guest identity or an authenticated success. Preserve separate workforce IAM sessions. |
| Consumer logout API | Authenticated, idempotent revocation command with a stable request ID; write revocation/audit on one held transaction connection. Repeated logout returns the same effective result. | Do not rely on an in-memory blacklist. A lost commit is reconciled by reading the session state; do not claim either success or retryable non-execution from an unknown outcome. |
| `AuthContext` and service worker | Send the server logout command using the current bearer before destroying its browser copy; immediately fence local offline replay and hide private UI. Confirm remote sign-out only after a conclusive server result. Preserve separate wording for offline/unknown server outcome. | An offline browser cannot guarantee remote revocation. It must not falsely show a completed server logout or retry a privileged command with an old bearer. A legitimate user may need to sign in again after a rollout cutover. |
| Additive schema, restricted role, deployment | Add a consumer-session authority only after applied migration 045/047 identity is reconciled. Grant the narrow web identity required to issue/verify/revoke; test non-superuser and non-`BYPASSRLS` behavior on disposable PostgreSQL and isolated staging. | Do not allocate a migration number now, edit applied SQL, piggyback on `users.updated_at`, or share workforce-session tables/credentials. |

**Session contract proposal:** An opaque `sid` is generated by CSPRNG; the DB stores `SHA-256(sid)` plus `user_id`, `issued_at`, `expires_at`, `revoked_at`, current refresh-token digest/version, and a non-sensitive revocation reason. The access JWT signs `sid`, `id`, `iat`, `exp`, and an explicit consumer-session contract version. The database row, not the token's role claim, grants authority. The controlling blueprint requires short-lived access and refresh rotation; therefore the current seven-day **access** JWT cannot be carried forward as a production contract. A candidate is a 15-minute access token with single-use rotating refresh and a seven-day maximum session lifetime, subject to security review and browser/storage threat modeling. Refresh reuse revokes or quarantines the session rather than issuing another credential. No raw bearer, refresh token or `sid` goes into logs or audit payloads. Unique digests and indexed active lookup bound verification cost. Retention/purge must follow an approved privacy schedule; none is currently approved.

**Rollout invariant:** Old stateless JWTs have no new session identifier and must be rejected once the new gate is active. Do not allow a seven-day grace path that reopens the old-worker replay window. Drain old server instances before declaring cutover, so no instance still accepts stateless tokens. Publish a forced reauthentication notice and test that an installed old worker's `/api/messages` POST receives 401. This can be achieved by requiring the new token contract without rotating the signing secret; secret rotation remains an optional separate operational control. The cutover has user-session disruption and needs a reviewed release window, but not a fictitious claim that an old client called a logout endpoint it never had.

**Acceptance tests:** (1) Mounted actual-server test: a legacy token still authenticates after current browser-only logout, then is denied after cutover; (2) newly issued short-lived session succeeds across two server processes; (3) revocation on one connection denies a previously valid token on another process and after restart; (4) conflicting account/session claims, unknown session and forged token fail closed; (5) revoked-role user loses authority even with an active session; (6) database outage and lost COMMIT preserve explicit unknown outcome; (7) refresh rotation, concurrent refresh and token-reuse detection preserve one active generation; (8) production-built old service worker with an already captured token cannot replay after logout/account switch or cutover; (9) offline logout is displayed as pending remote confirmation; (10) workforce login remains separate. Use sanitized local fixtures and disposable PostgreSQL first, then named staging with approved restricted roles. Do not substitute a browser-only purge test for the server result.

**Rollback/containment:** If the revocation authority fails before release, keep consumer sign-in behind the current release gate and restore the previous deploy artifact without reactivating generic worker replay. After cutover, never re-enable acceptance of legacy stateless tokens as a convenience rollback. A database outage returns an explicit authentication-dependency error for protected work; queue reconciliation retains unknown outcomes. No provider spend or customer-capital pilot is implied by completing this auth slice.

**Open dependencies:** Original applied `047_campaign_flight_controls_and_drain_requests.sql` is absent, local `045` differs from applied checksum, and isolated staging/restricted-role credentials are not configured. These block a new migration and deployed proof. Independent reviewer must accept the session/cutover policy, including the forced reauthentication impact, before the release command is scheduled. Local R1-03 tests and other dependency-ready cards can continue meanwhile.

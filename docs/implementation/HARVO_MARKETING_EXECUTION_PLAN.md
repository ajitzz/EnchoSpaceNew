## M1 impact analysis and implementation plan

Classification: Bug Fix / provider integration, with necessary tests and documentation. Root cause: Google adapter constructs local IDs and successful states instead of provider operations; transport silently simulates when credentials are missing and uses sunset versions; control/report methods similarly manufacture results. Existing server dispatch is unconditionally contained and does not call the Google adapter for creation.

Implement authenticated, bounded v25 REST calls with strict response/error validation, no implicit sandbox and no automatic mutation retries. Build only an explicitly specified Search campaign with distinct daily budget, real keywords/geo/language criteria, responsive-search text and a property landing URL. All spend-bearing objects are created paused. Accept only returned provider IDs; Google's negative temporary IDs are request-local references, never persisted as external IDs. Read back creation before declaring it verified. Capture a durable request before calling the provider; ambiguous outcomes remain quarantined and cannot republish under a fresh key.

Use the existing provider entity/transaction tables and a narrowly scoped schema migration if a campaign-level uniqueness boundary is required. Keep database transactions short and outside network waits. Duplicate calls must bind the same owner/campaign/request, while database/HTTP failures preserve evidence. Adapter reads query Google; failures must not become fabricated live states or metrics. Resume/budget/creative automation remain explicitly unavailable until their authorization milestone rather than pretending to apply them. Safety pause may be implemented with verified provider state.

Affected files: Google provider/client/error definitions, narrowly scoped Search publishing/persistence helpers, provider input types if needed, isolated test configuration and suites, a migration only if required, HARVO/Constitution/decision/incident records. No new property fields or host/admin design implementation in M1. HTTP/domain interfaces retain existing method signatures; new Google-specific input requirements and explicit errors are documented. Existing default-success tests must be replaced or clearly separated from current acceptance, not promoted as evidence.

Risks: provider-account eligibility cannot be proven offline; legacy callers may expect synthetic success; irreversible remote creation may succeed while its response is lost; persistence failure must not lead to blind retries; shared-account currency/identity cannot be guessed. The existing unconditional Google live-dispatch gate stays closed. No campaign activation, payment, production database migration or public deployment is part of M1 acceptance.

Verification: isolated Vitest config without dotenv/server startup; provider-shaped fake HTTP responses exercise real transport/payload code and negative paths; temporary real local PostgreSQL verifies claims/concurrency and transaction behavior without Neon access. Run typecheck/build and selected existing pure tests. Independent reviewer checks authorization, returned-ID provenance, failure semantics and integration containment. These checks do not establish Google account approval or live delivery; that remains M10.

Rollback: retain a scoped pre-edit file snapshot; revert M1 source only if needed, keeping Google dispatch contained. Never restore synthetic success as an operational fallback. Preserve transaction evidence and pause uncertain remote campaigns through authorized reconciliation. No destructive data rollback; any additive migration must have explicit forward/rollback guidance.

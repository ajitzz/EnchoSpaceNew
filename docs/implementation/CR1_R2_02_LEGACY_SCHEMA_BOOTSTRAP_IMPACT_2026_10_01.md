# R2-02 legacy schema bootstrap containment — impact before code

**Verified source.** `server.ts` loads `.env` and invokes `ensureDbInitialized()` on startup. Production uses read-only `databaseReadiness()`, but every other runtime can run legacy `CREATE TABLE`, `ALTER TABLE` and index statements against the selected URL when its fast check misses a column. `npm run dev` can therefore try DDL on the primary remote Neon endpoint. The separately repaired legacy interval gate does not cover this startup path.

**Narrow change and authority.** Preserve the production read-only readiness branch. Let non-production legacy schema bootstrap write only when an operator explicitly sets `HARVO_LOCAL_SCHEMA_BOOTSTRAP_ENABLED=local-disposable-only` and the selected PostgreSQL URL has a loopback hostname. Preserve the isolated test harness separately: `NODE_ENV=test`, `ENCHO_TEST_SANDBOX=1`, and a synthetic `encho-test.invalid` or loopback URL may initialize the pg-mem fixture. All other runtimes must take the read-only readiness path and fail rather than trying DDL. Do not alter migration bytes, the migration runner, schema checksum authority, finance, workers or APIs. A loopback proxy can still lead to a remote database; this is accidental-target containment rather than proof of database ownership.

**Failed fixture receipt and correction.** The first focused run had 9 failures in `auth_public_response.test.ts`: that existing isolated test deliberately sets `DATABASE_URL=postgres://localhost/encho-auth-fixture` before importing `server.ts`, while the initial guard allowed only the test runner's `encho-test.invalid` URL. It sent the pg-mem harness down production-style readiness, which pg-mem cannot parse, and OTP fixtures returned 500. The corrected test branch accepts loopback only with both exact test/sandbox markers; remote Neon-style URLs remain denied. Preserve this failure separately from the repaired run.

**Compatibility/security.** Remote development can no longer repair missing tables implicitly; operators must run reviewed migrations on an explicitly named target after reconciling history. Local disposable development may opt in. The startup catch still logs readiness failure; this change does not prove every route refuses all requests after a failed readiness check. The primary `.env` is not an approved staging/DDL target.

**Validation.** Test missing/incorrect opt-in, remote/malformed URL, production/serverless, exact isolated pg-mem test identity, and explicit local opt-in. Run mounted server/database tests through the sanitized Node 24 runner; typecheck, scoped lint and diff check. Do not run `npm run dev`, the migration runner, remote database commands or provider calls.

**Rollback/containment.** Keep remote development read-only and restore a compatible migration-backed schema through the reviewed migration process; never revert to implicit DDL against `.env`. If a local disposable fixture needs bootstrap, set the exact opt-in with a fresh local PostgreSQL URL. No applied migration SQL is modified.

**Repaired local receipt (1 October).** The mounted `auth_public_response` suite plus the schema/timer gate suites passed **43/43** after the fixture correction. The schema gate plus deployment-readiness suites passed **40/40**. Server TypeScript, scoped ESLint and `git diff --check` exited 0. The test runner stripped real database/provider credentials; no Neon apply, remote connection or startup of a live development server occurred. Read-only readiness behavior is covered by its existing suite, while the new guard is tested as a pure decision function and its `server.ts` call site was inspected. A full P2 phase-exit regression/build and a deployed restricted-role check remain open; R2-02 is still `IN_PROGRESS`.

**Additional source finding before follow-up code:** A source search found `ensureUsersTable()` and `ensureListingsTable()` called directly by auth/listing routes, and the long-running server `listen` callback has another `CREATE TABLE` block. The startup-only guard above therefore does not contain all implicit DDL. Extend the same source-of-truth predicate to both helpers: on remote/non-authorized targets they must perform the read-only readiness decision and refuse missing schema, never execute their CREATE/ALTER body. Require the exact predicate plus existing administrative-development opt-in for `/api/init-db`, and guard the listen callback's DDL block. Reuse the existing readiness checker; no new schema/migration or API contract. Test mounted auth paths and guard behavior, and run a source-level inventory for remaining direct route DDL. The latter may require a separate card and must not be silently declared solved.

**Follow-up implementation and limits:** Both helpers now use read-only readiness when the local bootstrap predicate is false. `/api/init-db` requires both its prior administrative-development flag and the local-disposable target; the listen callback's DDL block also requires that target. The focused mounted auth/schema-gate run reported **27/27** passing after the change, with server TypeScript, scoped ESLint and diff check exiting 0. The first receipt piped through `tail` and therefore had the shell pipeline's exit code rather than a trustworthy underlying test exit code; a separate pipefail rerun is required before citing that exit status. Other direct legacy DDL paths in `server.ts` are not yet inventoried or contained, so this is not a blanket claim that development against a remote URL is read-only. R2-02 and the deployed migration/restricted-role gates remain open.

**Pipefail verification:** Re-ran the two focused mounted auth/schema-gate files with shell `pipefail`; the underlying test command exited **0** and reported **27/27** passing. The earlier pipeline limitation is retained above as a provenance correction, not erased.

## Why six hours have not closed `CHANGES_REQUESTED`

1. **A scope mismatch keeps resetting the finish line.** F0 is a truthful, read-only media meter; F2 is per-flight presentation. R6-02 also requires four-flight state, canonical booking deduplication, consented attribution, captured versus fulfilled outcomes, refunds, pagination and cross-tenant proof. R5-04 separately owns incremental funding/top-up. A correct F0 patch cannot close R6-02 or R5-04. Review each bounded slice independently, but never weaken the controlling cards.
2. **The implementation was patched from the UI inward without one authoritative evidence contract.** Successive reviews found real cross-layer conflicts: retrieval time mistaken for provider data currency, identity projected from the current row rather than the stored report, UTC request end versus ad-account calendar, then an account timezone injected into a mock delivery truth that real adapters do not return. More assertions of the same mock shape could not expose these defects. The repair needs one typed provider-owned calendar/report identity contract, server-side compatibility decision and a host-safe projection; the UI must not reconstruct account authority.
3. **The calendar repair was incomplete at the first snapshot.** `src/lib/providers/AdProvider.ts` declares `getServingAccountReportingCalendar`, and Meta/Google adapters implement it. The worker uses it and no longer selects old telemetry timezone as current authority. At 18:51 it did not compare returned snapshot account/timezone to the calendar. At 18:54 it added conditional comparisons. A missing metadata field can still bypass those comparisons; require the provider adapter's expected account/timezone evidence or mark the report unavailable. Calendar lookup failures are caught without an explicit reason code; unknown account evidence must remain unknown and trigger protection/reconciliation.
4. **The fallback view was not truthful at the first snapshot.** On `ACCOUNT_TIMEZONE_UNAVAILABLE`, the worker retained prior telemetry while the meter hid its amount. At 18:54 Antygravity added a historical/stale branch after compatibility checks. That is a substantive repair pending a frozen test. A prior amount must never be shown if campaign, revision, provider, authorized budget or serving-account binding changed; a server-attested last-successful receipt is stronger than client inference.
5. **No-call states were mislabeled at the first snapshot.** `NOT_STARTED` recorded an inverted fictitious request window though no API call occurred. Antygravity changed those fields to null by 18:54; independent no-call test and review are still required.
6. **The proof boundary is narrower than the claims around it.** The newer route test runs a mocked provider through worker → disposable PostgreSQL → authenticated workspace → a pure meter normalizer. A separate mounted Studio test uses mocked workspace data. There is no single mounted browser test consuming real route JSON, no adapter account-response test in this slice, no current full regression and no authenticated live Meta/Google readback. Passing targeted tests is useful local evidence, not F0 integration or R6-02 acceptance.
7. **The worktree is not a stable review unit.** More than 160 mixed staged/unstaged paths and actively changing source make a report/diff hash obsolete minutes later. The same source cannot be fairly accepted while another writer edits it. Freeze a small source subject, capture HEAD/index/tree/diff hashes, then independently review that exact subject. Integrate reviewed paths into the primary checkout through a deliberate scoped change; do not assume worktrees share uncommitted files.

## Escape plan

1. **Freeze and name one review subject.** Stop overlapping edits on the fuel paths, record HEAD/index/worktree diff and scope; keep other dirty work intact. Review F0 separately from R6-02 and R5-04.
2. **Finish the F0 contract at the server boundary.** Resolve the current serving-account calendar from typed adapters and local provider-entity binding; compare snapshot account ID/timezone, provider, external campaign, revision, authorized budget, currency and report window before persistence. On disagreement or unavailable evidence, preserve only a separately identified compatible last-successful receipt, label it historical, and issue protection/reconciliation. Do not expose master account IDs to hosts.
3. **Correct no-call/fallback semantics.** `NOT_STARTED` and unavailable-calendar report windows are null. Previously verified compatible spend remains visible as dated/stale after a temporary failure; incompatible history remains withheld. Neither is reported zero/current.
4. **Prove the actual chain.** Adapter fake-client tests; worker → disposable PostgreSQL → mounted authenticated route → mounted Host Studio at mobile and desktop sizes; stale account, changed timezone, west/east midnight, ended flight, corrected report, no prior report, and hostile tenant cases. Run targeted suites/typecheck/scoped diff check on a frozen subject, then independent review. If accepted, say `F0 READY_FOR_REVIEW` or `F0 ACCEPTED_LOCAL` with exact scope; **do not** mark R6-02 complete.
5. **Then close R6-02 as a distinct product journey.** Build four-flight distinct booking aggregate by canonical booking identity, captured/fulfilled/cancelled separation, consented attribution, delayed corrections and isolated host scope. Exercise pause independence, pagination and built UI. R5-04 top-up follows approved COMM/legal rules, provider capability and independent finance tests; do not use the old wallet route.
6. **Treat release separately.** Integrate reviewed paths into primary, run required full phase-exit checks, resolve migration/evidence drift and authentic staging/provider/legal/pilot gates. No live spend from this review.
